# 第 6 章 — 插件架构

安全评估平台必须持续演进——新漏洞出现、新安全控制出现、新合规框架引入。没有评估引擎能永久地将每种安全能力嵌入其核心。Asscor 因此采用面向插件的架构——新功能应通过插件引入，而非扩展内核。

插件架构的设计目标：可扩展性、隔离性、可维护性、解耦。在 Asscor 中，插件是能力提供者，不应成为微型运行时。运行时拥有执行权，插件提供专门功能。

每个插件遵循受管理的生命周期：发现 → 注册 → 初始化 → 执行 → 健康监控 → 卸载。

插件自然分为几类：证据提供者（配置检查、主机检查、容器检查、云检查）、知识提供者（ATT&CK 映射、威胁情报、合规配置文件）、评估扩展（自定义领域、组织特定规则、专用评分逻辑）、输出提供者（CLI、JSON、HTML、API、仪表盘）。

插件通过运行时契约与平台交互，不应直接依赖内部运行时结构。插件故障应保持隔离——初始化失败、执行失败、超时、依赖失败时，运行时应在可能的情况下继续运行。插件接口应比插件实现更慢地演进——稳定合约允许独立开发。

架构风险包括插件间直接通信（应通过运行时服务）、评估规则泄漏到插件、插件直接依赖内核内部。随着生态系统的增长，插件架构可能演进为评估市场——每种贡献不同能力，运行时提供统一执行环境。插件不负责定义评估理论——保持可扩展性与推理之间的分离。
