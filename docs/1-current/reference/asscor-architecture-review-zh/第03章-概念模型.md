# 第 3 章 — 概念模型

## 3.1 引言

Asscor 不把安全评估视为漏洞计数，而是将其建模为对运行证据的推理过程。目标不是判断漏洞是否存在，而是判断当前运行状态是否可接受。

## 3.2 核心概念

五大基本概念：**证据 → 上下文 → 策略 → 评估 → 决策**。每个概念代表评估过程中一个独立的职责。

## 3.3 证据

证据代表可观察的安全事实——不包含决策，不包含建议，仅描述现实。例如：开放端口、SELinux 禁用、备份缺失、弱密码策略、完整性校验失败。证据是客观的，回答"正在发生什么？"

## 3.4 上下文

相同的证据可能在不同环境下产生不同结论。例如 SSH 暴露在互联网上可能不可接受，而相同配置在隔离的实验室网络中可能可接受。上下文因此修改对证据的解读，回答"证据存在于何处？"

典型上下文包括：业务环境、网络暴露、资产关键性、信任边界、组织角色。

## 3.5 策略

策略定义组织期望。不同于证据（描述性），策略是规范性的。例如——证据："密码长度=8"、策略："最小密码长度=12"。策略决定证据是否满足组织要求。不同组织可能定义不同策略，因此可接受性取决于组织而非普适固定。

## 3.6 评估

评估代表推理过程——将证据、上下文、策略转化为运行判断。评估 = f(证据, 上下文, 策略)。评估过程本身独立于任何特定评估算法，允许多个评估引擎共存（SSAM、未来概率模型、贝叶斯引擎、规则引擎）。

## 3.7 决策

决策是评估过程的最终输出。不同于原始分数，决策代表运行建议。例如"可接受"、"受限"、"不可接受"。分数是实现细节，运行决策代表真正的目标。

## 3.8 职责分离

概念模型有意分离职责。每一层有单一职责：
- 证据：收集现实
- 上下文：描述环境
- 策略：定义期望
- 评估：推理
- 决策：支持运营

## 3.9 评估流水线

完整工作流：证据收集 → 证据归一化 → 上下文解析 → 策略匹配 → 评估 → 决策 → 建议。每个阶段可以独立演进，评估引擎因此与证据提供者解耦。

## 3.10 工程映射

概念模型自然映射到项目架构：
- 证据 → 收集器、插件、适配器
- 评估 → SSAM
- 决策 → 报告、API、CLI

工程实现应保持为概念模型的实现，而非定义模型本身。

## 3.11 设计原则

证据优先、上下文感知、策略驱动、引擎独立、决策导向。最终目标是运行决策支持而非分数生成。

## 3.12 本章总结

评估过程被建模为从可观察证据到运行决策的转换，经过上下文感知的推理和策略评估。后续各章描述这一概念模型如何由评估引擎和运行时架构实现。
