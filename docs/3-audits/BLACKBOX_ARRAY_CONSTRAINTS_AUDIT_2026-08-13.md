# 黑盒阵列约束审计：判断依据 + 全票丢弃 + 扩展包 + 性能体积

**日期**: 2026-08-13 | **版本**: v0.2.3 | **性质**: 黑盒阵列方案的四个新增约束可行性评估

---

## 一、四个新增约束

| 约束 | 内容 | 本质 |
|:---:|------|------|
| C1 | 黑盒数据必须带**详细判断依据** | 黑盒输出可解释性 |
| C2 | 最终过滤只能**所有黑盒都选过滤才丢弃** | 全票丢弃（最大化召回） |
| C3 | 方案必须用**扩展包形式**实现 | 不改内核核心 |
| C4 | 黑盒带来**性能消耗 + 体积膨胀**（阵列/多阵列/阵列组） | 资源约束 |

---

## 二、约束可行性评估

### C1: 黑盒输出必须带详细判断依据 — ⚠️ 部分可行

| 判断依据类型 | 可行性 | 说明 |
|------|:---:|------|
| 置信度分数 | ✅ 易 | 模型 softmax/概率输出 |
| 触发的特征/模式 | ✅ 可 | 决策树路径、规则命中 |
| 特征重要性 | 🟡 中 | 需 LIME/SHAP 类局部解释 |
| 深度模型的可解释依据 | 🔴 难 | Transformer 等难提供"详细依据" |

**裁定**: 可通过**限制黑盒模型类型**（优先可解释模型：决策树/规则型/线性模型）满足 C1。深度模型作为"不可解释"类需单独标注，仅作辅助。本质是"用模型可解释性换审计可追溯性"。

### C2: 全票丢弃（所有黑盒都过滤才丢弃）— ✅ 可行但误报极高

```
语义: 阵列中任一黑盒认为"可疑/不确定" → 保留
      阵列中所有黑盒一致认为"噪声" → 才丢弃
```

| 特性 | 影响 |
|------|------|
| 召回率 | 🟢 最大化（宁可误报不可漏报） |
| 误报率 | 🔴 极高（N 个模型的误报并集） |
| 白盒负载 | 🔴 洪泛（大量候选信号涌入） |

**关键推论**: C2 与"召回层"定位**高度一致**——最大化召回是召回层的使命。但 C2 的极端保守意味着白盒仲裁层会收到海量误报，需要白盒有**高效的快速过滤**能力，否则白盒被噪声淹没。

### C3: 扩展包形式 — 🔴 与前审计结论冲突

前审计（EXTENSION_LIFECYCLE_FEASIBILITY）已确认：

| 扩展包能力 | 状态 |
|------|:---:|
| 定义新扩展点 | ❌ 不能（RegisterPoint 平台专属） |
| 注入新接口 | ❌ 不能（外部进程够不着 DI） |
| 跑常驻状态机 | ❌ 不能（30s 超时强杀） |

**冲突点**: C2 的"全票丢弃"仲裁逻辑需要**收集多个黑盒输出并判断**，这是常驻状态逻辑。而扩展包（extmgr）是无状态外部进程。

**唯一出路**: 用 **build-tag 可选模块**（如 attck-ext-pack 模式）实现，而非 extmgr 运行时扩展包。但 build-tag 模块需要重新编译内核，违背"扩展包"的"不改内核"语义。

**裁定**: C3 存在**结构性矛盾**，需在以下两者间选择：
- A. 接受 build-tag 模块（optional/ 目录，编译期集成，不需运行时改内核）
- B. 黑盒阵列作为独立推理服务（边车模式），通过既有扩展点 + gRPC/REST 通信

### C4: 性能/体积 — 🔴 核心现实约束

#### 4.1 体积膨胀量化

| 模型类型 | 单模型体积 | 推理硬件 | 阵列（N=3）体积 |
|------|:---:|:---:|:---:|
| 规则型（决策树） | ~1-10 MB | CPU | ~3-30 MB |
| 传统 ML（XGBoost） | ~10-100 MB | CPU | ~30-300 MB |
| 深度学习（Transformer） | ~100 MB-10 GB | GPU | ~300 MB-30 GB |

#### 4.2 性能消耗量化

| 推理位置 | 推理延迟 | 资源占用 | 可行性 |
|------|:---:|:---:|:---:|
| 边缘主机（agent） | 需 <100ms | CPU 受限 | 仅轻量模型 |
| 内核（kernel） | 需 <1s | 共享 CPU | 中量级 |
| 独立推理服务 | 无硬限制 | 独立资源 | 重量级 |

#### 4.3 组合爆炸

```
单阵列: N 个模型 → N×推理开销
多阵列: M 个阵列 × N 模型 → M×N×开销
阵列组: K 组 × M 阵列 × N 模型 → K×M×N×开销
```

例：2 阵列组 × 3 阵列 × 3 模型 = 18 个模型，若每模型 100 MB = 1.8 GB 体积。

## 三、约束间的矛盾矩阵

| 冲突 | 涉及约束 | 矛盾点 |
|------|:---:|------|
| **扩展包 vs 全票丢弃** | C2 × C3 | 仲裁逻辑需常驻状态，扩展包无状态 |
| **判断依据 vs 性能** | C1 × C4 | 详细依据的生成（LIME/SHAP）额外开销 |
| **全票丢弃 vs 性能** | C2 × C4 | 保守策略增加候选量，加重白盒负载 |
| **多阵列 vs 体积** | C4 | 阵列组组合爆炸 |

---

## 四、可行的架构折中方案

### 方案A：分层推理（推荐）

```
边缘(agent)     内核(kernel)      独立推理服务
  │                │                  │
  └─ 轻量模型 ──→ 中量模型 ──→ 重量模型
     (规则型)      (XGBoost)      (深度学习)
     内嵌agent     内嵌内核        边车/gRPC
```

- 轻量模型内嵌 agent（体积可控，<10 MB）
- 中量模型内嵌内核或独立服务
- 重量模型独立部署（GPU 服务器）

### 方案B：build-tag 模块（满足 C3 语义最接近）

- 黑盒阵列作为 `optional/algorithms/packages/blackbox-recaller/` 的 build-tag 模块
- 用 `RoleAdvisory` + `MergeWhiteboxFirst`（前审计结论）隔离
- 全票丢弃仲裁逻辑在模块内（进程内，可跑常驻）

### 方案C：独立推理边车（满足 C3 运行时语义）

- 黑盒阵列作为独立服务，通过 HTTP/gRPC 暴露推理 API
- 内核通过 `adapter` 或既有扩展点调用
- 体积/性能隔离到独立服务，不影响内核

## 五、最终裁定

**四个约束不能同时完全满足，需排序取舍。**

| 约束 | 优先级 | 裁定 |
|:---:|:---:|------|
| C4（性能/体积） | 🔴 最高 | **决定架构**，必须分层推理 |
| C2（全票丢弃） | 🟡 高 | 可满足，但需白盒高效过滤 |
| C1（判断依据） | 🟡 高 | 限制模型类型（可解释优先） |
| C3（扩展包） | 🟢 中 | 需放宽为"build-tag 模块或边车" |

**推荐组合**：方案A（分层推理）+ 方案B（build-tag 模块）+ C1（可解释模型优先）+ C2（全票丢弃）。

具体：
1. 轻量可解释模型（决策树/规则）内嵌 agent，满足 C1 + C4
2. 黑盒阵列作为 build-tag 可选模块，满足 C3 语义
3. 全票丢弃仲裁逻辑在模块内，满足 C2
4. 重量模型独立边车部署，满足 C4

**核心结论**：C4（性能/体积）是压倒性约束，决定了不能"多阵列组"无脑堆模型，必须先做**模型分层 + 推理卸载**。C3（扩展包）需在"build-tag 模块"和"独立边车"间选择，前者贴近"可选模块"，后者贴近"运行时扩展"。
