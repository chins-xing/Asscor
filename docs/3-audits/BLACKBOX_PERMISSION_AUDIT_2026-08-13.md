# 黑盒阵列权限限制与直接攻击向量审计

**日期**: 2026-08-13 | **版本**: v0.2.3 | **性质**: AI 黑盒模型安全性的补充——权限隔离 + 主动攻击防御

---

## 一、核心结论

**现有 ASSCOR 的权限限制机制对黑盒模型不充分，黑盒阵列需要"进程级隔离 + 最小权限 + 单向数据流"三层额外防御。**

黑盒阵列不只是"被投毒的输出源"，而是**活跃的攻击者**——被攻破后可作为跳板攻击内核、可主动发起注入攻击、可耗尽资源、可窃取数据。

---

## 二、现有权限限制能力评估

ASSCOR 已有如下权限限制（此前审计确认）：

| 现有机制 | 覆盖的攻击面 | 对黑盒模型的覆盖度 |
|------|------|:---:|
| 命令白名单（19 二进制 + 16 shell） | Shell 注入 | 🔴 不适用（模型不是命令） |
| SHA-256 二进制校验 | 供应链篡改 | 🟡 防篡改，防不了逻辑后门 |
| 脚本适配器 root 所有权校验 | 脚本越权 | 🔴 不适用 |
| Shell 元字符过滤 | 命令注入 | 🔴 不适用 |
| 路径穿越防护 | 文件访问 | 🟡 部分覆盖 |
| 30s 超时强杀 | 进程挂起 | 🟡 只防挂起，不防资源耗尽 |

**结论**: 现有机制面向"外部脚本/命令"，对"黑盒模型推理"这一新形态**基本不覆盖**。

---

## 三、直接来自黑盒阵列的攻击向量

### 3.1 模型文件攻击

| 攻击 | 机制 | 危害 |
|------|------|:---:|
| **恶意反序列化** | pickle 等反序列化执行任意代码 | 🔴 RCE |
| **恶意算子** | 模型自定义算子注入恶意代码 | 🔴 RCE |
| **权重后门** | 权重文件隐藏触发器 | 🔴 逻辑后门 |

### 3.2 推理接口攻击

| 攻击 | 机制 | 危害 |
|------|------|:---:|
| **提示注入** | LLM 被注入指令执行恶意操作 | 🔴 越权 |
| **输出注入** | 模型输出含 SQL/命令注入 payload | 🔴 二次注入 |
| **资源耗尽** | 推理请求恶意构造导致 CPU/GPU 过载 | 🟡 DoS |

### 3.3 数据攻击

| 攻击 | 机制 | 危害 |
|------|------|:---:|
| **模型反演** | 从输出反推训练数据 | 🔴 数据泄露 |
| **数据窃取** | 模型进程读取内核敏感数据 | 🔴 横向窃取 |
| **横向移动** | 被攻破模型作跳板攻击内核 | 🔴 提权 |

## 四、严格权限限制设计（三层防御）

### 4.1 第一层：进程级隔离

| 措施 | 说明 |
|------|------|
| **容器化** | 黑盒模型跑在独立容器（gVisor/微 VM），与内核进程隔离 |
| **seccomp** | 限制黑盒进程可用的系统调用白名单 |
| **AppArmor/SELinux** | MAC 强制访问控制，黑盒无法访问内核资源 |
| **独立用户** | 黑盒以专用非特权用户运行，无 root |

### 4.2 第二层：最小权限

| 措施 | 说明 |
|------|------|
| **只读挂载** | 黑盒只能读模型文件 + 输入数据，不能写 |
| **网络白名单** | 黑盒仅允许访问推理服务，禁止访问内核网络 |
| **无文件系统写权限** | 黑盒不能写任何文件（含日志，用管道回传） |
| **cgroup 限制** | CPU/内存/GPU 配额，防资源耗尽 |

### 4.3 第三层：单向数据流

```
原始数据 ──→ [黑盒阵列] ──→ 候选信号
              (只读输入)      (只写输出)
              ❌ 不能读内核  ❌ 不能写内核
              ❌ 不能网络    ❌ 不能文件
```

**核心原则**：黑盒阵列是"纯函数"——输入原始数据，输出候选信号，无任何副作用（无文件/网络/内核访问）。所有副作用通过白盒侧的受控接口完成。

## 五、针对直接攻击的防御

### 5.1 模型加载安全

| 防御 | 说明 |
|------|------|
| **禁用 pickle** | 用安全序列化格式（ONNX/SafeTensors）替代 pickle |
| **模型签名验证** | 加载前验证模型签名（防篡改，防不了逻辑后门） |
| **算子白名单** | 仅允许内置算子，禁止自定义算子 |

### 5.2 输出消毒

| 防御 | 说明 |
|------|------|
| **输出视为不可信** | 黑盒输出的每个字段做注入检测（SQL/命令/路径） |
| **白盒复核** | 黑盒信号经白盒规则验证后才进入决策 |
| **类型严格校验** | 输出字段类型/范围/格式严格校验，拒绝异常 |

### 5.3 资源限制

| 防御 | 说明 |
|------|------|
| **推理超时** | 单次推理硬超时，超时即丢弃 |
| **并发配额** | 限制并发推理数，防洪泛 |
| **cgroup 配额** | CPU/内存/GPU 硬限制 |

## 六、可行性裁定

### 6.1 权限限制的可行性

| 层 | 可行性 | 说明 |
|------|:---:|------|
| 进程级隔离 | ✅ 可 | 容器化/seccomp/AppArmor 成熟 |
| 最小权限 | ✅ 可 | 只读/无写/网络白名单可做 |
| 单向数据流 | ✅ 可 | 纯函数模型可做 |

### 6.2 直接攻击防御的可行性

| 攻击 | 防御可行性 | 说明 |
|------|:---:|------|
| 恶意反序列化 | 🟢 可防 | 禁用 pickle + 安全格式 |
| 提示注入 | 🔴 难防 | LLM 提示注入无成熟防御 |
| 逻辑后门 | 🔴 难防 | 权重后门无法形式化检测 |
| 资源耗尽 | 🟢 可防 | cgroup + 超时 |
| 数据窃取 | 🟢 可防 | 单向数据流 + 只读 |

---

## 七、最终裁定

**权限限制和单向数据流是可落地的（进程隔离 + 最小权限 + 纯函数模型），能防住大部分"直接攻击"。**

但有两个**无法完全防御**的攻击面：

| 不可防攻击 | 原因 |
|------|------|
| **逻辑后门** | 权重后门无法形式化检测，防了篡改防不了后门 |
| **提示注入** | LLM 提示注入无成熟防御（新兴未解难题） |

### 核心结论

1. **权限限制是必要的**——黑盒阵列必须"进程级隔离 + 最小权限 + 单向数据流"，这是能防住直接攻击的底线
2. **但权限限制防不住逻辑后门和提示注入**——这两个是 AI 安全领域的未解难题
3. **结论与上一轮一致**——黑盒阵列不能成为主路径，白盒独立探测通道必须保持主路径 + 兜底
4. **黑盒阵列的信任边界**：即使有严格权限限制，黑盒输出仍视为不可信输入，白盒复核

### 与前七轮审计的递进

```
混合架构红线 → 编排器 RoleAdvisory → 召回层 → 四约束 → 部署形态
→ AI 自身安全性 → 权限限制 + 直接攻击防御
```

这条审计链从"架构隔离"层层深入到"权限隔离"和"主动攻击防御"，最终结论收敛为一个核心原则：

**黑盒阵列无论架构隔离多好、权限限制多严，其输出本质仍是"不可形式化验证的信任边界"，必须始终视为不可信输入，由白盒确定性验证兜底。**
