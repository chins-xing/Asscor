## 发现项

### [A-1] ConfigWatcher 对 AssessorInterface 的依赖在 Init 时无法解析 — High
- **位置**：[config_watcher.go:L43-L46](file:///f:/Argus/internal/kernel/config_watcher.go#L43-L46)
- **描述**：ConfigWatcher（Priority=1）在 `Dependencies()` 中声明了对 `AssessorInterface` 的依赖，并在 `Init()` 中通过 DI 容器解析。但 AssessorModule 的 Priority=40，其 `Init()` 在 ConfigWatcher 之后才执行，DI 绑定尚未建立。导致 `m.assessor` 始终为 nil，配置热加载时无法触发 Assessor 的重载逻辑。
- **代码**：
  ```go
  // config_watcher.go:L43-L46
  func (m *ConfigWatcherModule) Dependencies() []PluginDependency {
      return []PluginDependency{
          {Name: "assessor", Interface: (*AssessorInterface)(nil)},
      }
  }

  // config_watcher.go:L57-L62 — Init 时解析，此时 Assessor 尚未 Init
  if impl, ok := kc.Container().Resolve((*AssessorInterface)(nil)); ok {
      m.assessor = impl.(AssessorInterface)
  }
  ```
- **风险**：配置热加载时 Assessor 不接收新配置，SSAM 权重、SPC 配置等变更不会在下一次评估中生效。
- **修复方案**：
  - 方案 A：将依赖解析从 `Init()` 移至 `Start()` 方法（推荐）——此时所有插件的 `Init()` 均已执行完毕
  - 方案 B：将 ConfigWatcher 的 Priority 提升到比 Assessor 更高但可以让 Assessor 先 Init 的值（需重新设计优先级分层）
  - 方案 C：通过 Bus 发布 `TopicConfigReloaded` 事件，让 Assessor 订阅而非 ConfigWatcher 主动调用

### [M-1] spc.go 文件过大（超过 1100 行） — Medium
- **位置**：[spc.go](file:///f:/Argus/internal/kernel/spc.go)
- **描述**：`spc.go` 包含 29 个函数，最后一个函数位于第 1110 行，远超 500 行的建议上限。文件混合了多种职责：数据类型定义（MatchType、ExposureLevel、ControlLevel）、插件生命周期、CMDB 资产管理、评分计算、CPE 匹配、暴露评估、控制水平评估。
- **风险**：文件过大导致代码导航困难，增加了维护成本和修改风险。
- **修复方案**：按职责拆分：
  - `spc_types.go`：数据类型定义（MatchType、ExposureLevel、ControlLevel、SPCAction 等）
  - `spc_plugin.go`：插件生命周期方法（Info/Dependencies/Priority/Init/Start/Stop/State/HealthCheck）
  - `spc_calculator.go`：评分计算逻辑（Calculate、matchCPE、determineExposure、determineControlLevel 等）
  - 保留 `spc.go` 作为聚合入口重导出

### [P-1] SPC CVE 缓存构建时未预分配切片容量 — Medium
- **位置**：[spc.go 多处](file:///f:/Argus/internal/kernel/spc.go)
- **描述**：在 CVE 缓存构建过程中，多个切片使用 `make([]T, 0)` 未预分配容量，导致 `append` 时多次触发底层数组扩容和内存拷贝。
- **代码**：`spc.go:L728-L737` 区域存在多处 `make([]cpeIndexEntry, 0)` 模式
- **风险**：CVE 缓存规模可达 100,000 条，频繁内存重分配会对 GC 造成压力。
- **修复方案**：在已知最终容量时使用 `make([]T, 0, estimatedSize)` 预分配，或基于 `len(cves[i].AffectedCPEs)` 计算预估容量。

### [P-3] Persistence 模块文件写入未使用缓冲 I/O — Low
- **位置**：[persistence.go:L139-L172](file:///f:/Argus/internal/kernel/persistence.go#L139-L172)
- **描述**：JSONL 写入操作未使用 `bufio.Writer` 包装，每次写入都可能触发系统调用。
- **风险**：在高频写入场景（如 Agent 心跳批次）下，无缓冲 I/O 会导致吞吐量下降。
- **修复方案**：使用 `bufio.NewWriter(file)` 包装文件句柄，配合定期 `Flush()` 或使用 `defer writer.Flush()`。

### [M-2] ConfigWatcher 优先级声明与依赖不匹配 — Low
- **位置**：[config_watcher.go:L43-L46](file:///f:/Argus/internal/kernel/config_watcher.go#L43-L46)
- **描述**：ConfigWatcher 的 `Dependencies()` 声明依赖 `AssessorInterface`，但实际 `Init()` 中使用 comma-ok 模式，依赖解决失败时静默跳过。这种"可选依赖"模式与 `Dependencies()` 返回强依赖列表的语义不一致。
- **风险**：`Dependencies()` 方法会误导开发者认为该依赖是硬性要求。
- **修复方案**：若依赖是可选的，应从 `Dependencies()` 中移除，仅在 `Init()` 中尝试解析并记录警告。

## 最终建议

1. **立即修复（High）**：ConfigWatcher 对 AssessorInterface 的依赖解析时机——将 `Resolve` 从 `Init()` 移至 `Start()`，或改用 `TopicConfigReloaded` 事件传播
2. **计划修复（Medium）**：同步所有白皮书中的模块优先级值与实际代码值
3. **计划修复（Medium）**：拆分 `spc.go`（1100+ 行）为 3 个文件
4. **计划修复（Medium）**：SPC CVE 缓存构建时预分配切片容量
5. **低优先级**：Persistence 模块添加缓冲 I/O；ConfigWatcher 移除声而不用 AssessorInterface 依赖声明

**整体评价**：ASSCOR 项目在安全、并发、业务逻辑三个核心维度表现优秀，未发现 Critical 级别问题。唯一的 High 级别问题（ConfigWatcher 依赖解析时机）属于架构设计层面的时序耦合，不会导致崩溃（有 nil 检查），但会导致配置热加载功能在特定路径下失效。
