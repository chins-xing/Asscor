# 黑盒+白盒混合架构可行性审计

**日期**: 2026-08-13 | **版本**: v0.2.3 | **性质**: 未来主方向可行性评估

---

## 一、现有白盒属性清单（破坏面基线）

ASSCOR 当前的核心差异化优势是**全链路确定性白盒**。审计现有白盒属性：

| 模块 | 白盒属性 | 证据 |
|------|---------|------|
| **SSAM 2.0 评分** | 纯函数、零依赖、零 goroutine、零锁 | `ssam-lib/formulas.go` 乘法加权公式 |
| **Prism 三层引擎** | 纯函数、注释引用白皮书章节号 | `prism-lib/core.go` 注释 `§14.7` |
| **SPC 漏洞评分** | 确定性公式 `0.20×CVSS+0.50×EPSS+0.30×KEV` | `spc.go:513` |
| **策略引擎** | 确定性阈值状态机 (OK/Warning/Critical/Isolated) | `policy.go` |
| **ATT&CK 归因** | 贝叶斯但可解释 (TTP 60% + IOC 40%) | `attck_apt_attribution.go` |
| **审计报告** | HMAC 签名 + 确定性生成 | `integrity/sign.go` |

**白盒本质**: 每一步决策可追溯到公式/规则/阈值，第三方可复现验证。

## 二、混合架构划分的可行性

用户划分**原则正确**，判定如下：

### 2.1 白盒清单（必须白盒）— 全合理

| 层级 | 审计结论 | 理由 |
|------|:---:|------|
| 状态机 LifecycleEngine | ✅ 合理 | 循环/终止/归档决策必须可追溯 |
| 定位聚合 Locator | ✅ 合理 | 攻击者位置可解释、可质疑 |
| 阻断调度 Blocker | ✅ 合理 | 阻断动作需明确触发原因 |
| 策略引擎 Policy | ✅ 合理 | 响应决策需规则依据 |
| 扩展点触发 | ✅ 合理 | 触发外部扩展的条件需确定性 |
| 审计报告生成 | ✅ 合理 | 审计本身不可黑盒化 |

### 2.2 黑盒清单（可以黑盒）— 需约束

| 层级 | 审计结论 | 前提条件评估 |
|------|:---:|------|
| 攻击者轨迹预测 | ⚠️ 可，但**高风险** | 输出作为 Locator 增强数据源——但"增强"的边界需严定义 |
| 异常模式识别 | ✅ 可 | 异常信号→白盒规则→响应，边界清晰 |
| 动态拓扑映射 | ✅ 可 | 拓扑更新→白盒确认，边界清晰 |

### 2.3 划分标准 — 完整且可执行

五条判断标准（决策者/输出/审计/失败定位/责任）覆盖了核心语义，是**可落地的红线**。

## 三、对现有白盒属性的破坏面积

### 3.1 破坏面积评估

| 黑盒引入点 | 破坏的白盒属性 | 破坏面积 | 缓解条件 |
|------|------|:---:|------|
| **轨迹预测** | Locator 的确定性 | 🔴 **大** | 预测仅作参考，Locator 决策仍走白盒归因 |
| **异常识别** | 检测的确定性 | 🟡 中 | 异常信号需白盒阈值二次判断 |
| **拓扑映射** | 拓扑的确定性 | 🟢 小 | 映射结果需白盒子网重叠确认 |

### 3.2 关键破坏风险（3 处红线）

| 风险 | 场景 | 后果 |
|------|------|------|
| **R1: 置信度误用** | 黑盒输出的 confidence 被直接当作决策阈值 | 白盒策略引擎被旁路 |
| **R2: 训练数据偏见** | 黑盒模型用非公开数据训练 | 评分结果不可复现、不可审计 |
| **R3: 不确定性忽略** | 黑盒概率输出被当确定性事实 | 审计报告失真 |

### 3.3 破坏面积的具体技术点

| 现有白盒代码 | 黑盒侵入后破坏 | 破坏面积 |
|------|------|:---:|
| `policy.go` 阈值状态机 | 黑盒置信度直接改状态 | 🔴 破坏确定性响应 |
| `ssam-lib` 纯函数评分 | 黑盒预测参与加权 | 🔴 破坏可验证性 |
| `integrity/sign.go` HMAC | 黑盒输出纳入签名但不可复现 | 🟡 破坏审计一致性 |
| `spc.go` CVE 公式 | 黑盒异常分数替换 CVSS | 🟡 破坏确定性评分 |
| `prism-lib` 风险扩散 | 黑盒预测替代子网传播 | 🟡 破坏可解释风险 |

## 四、可行性裁定

**混合架构可行，但必须守住一条红线：**

> **黑盒输出永远不能直接驱动白盒决策。黑盒只能作为"感知层"产生概率性信号，最终决策必须经过白盒规则的确认与仲裁。**

### 守住红线的具体约束

| 约束 | 实现方式 |
|------|------|
| 黑盒输出必须附带**置信度** | 白盒规则对置信度设阈值，低于阈值丢弃 |
| 黑盒输出必须**可复现**（固定 seed）或标注非确定性 | 审计报告区分"确定性结果"与"参考信号" |
| 黑盒模型**不进审计报告主体** | 审计报告只记白盒决策；黑盒信号单独附注 |
| 黑盒异常**不直接触发阻断** | 异常→白盒策略→阻断，两级仲裁 |

### 推荐落地顺序

| 阶段 | 内容 | 风险 |
|:---:|------|:---:|
| 1 | 拓扑映射黑盒化（最安全） | 🟢 低 |
| 2 | 异常识别黑盒化（需白盒仲裁） | 🟡 中 |
| 3 | 轨迹预测黑盒化（最后，风险最高） | 🔴 高 |

## 五、结论

1. **划分原则正确** — "决策必须白盒、感知可黑盒"是安全领域成熟架构（类 SIEM+SOAR 的检测/响应分层）。
2. **破坏面积可控** — 只要守住"黑盒不直接驱动决策"红线，对现有 6 个白盒模块的破坏面积集中在 Locator/检测层，不影响 SSAM/Prism/SPC 的确定性评分核心。
3. **最大风险是置信度误用** — 必须在接口层强制"黑盒输出 = 信号 + 置信度"，白盒仲裁后才能成为决策。
4. **现有白盒优势应保留** — SSAM/Prism 的"纯函数、可复现、注释引用白皮书"是 ASSCOR 的护城河，混合架构应在**外围感知层**引入黑盒，而非侵入评分核心。
