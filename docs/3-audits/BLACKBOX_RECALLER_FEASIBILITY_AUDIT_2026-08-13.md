# 多黑盒阵列负责初步信息筛选 可行性审计

**日期**: 2026-08-13 | **版本**: v0.2.3 | **性质**: 黑盒+白盒混合架构的架构定位细化

---

## 一、核心结论

**可行，且是比前两轮方案更优的架构定位。**

"多黑盒阵列负责初步信息筛选"把黑盒从"感知增强"降级为**"召回层（Recaller）"**，边界比之前更清晰：黑盒只做"筛"（从海量原始数据中标记候选风险信号），白盒做"断"（确定性验证 + 决策）。这天然契合"召回层 + 精确层"两阶段架构，对白盒属性的破坏面积**进一步缩小**。

---

## 二、架构定位对比（三轮演进）

| 轮次 | 黑盒定位 | 边界清晰度 | 破坏面积 |
|:---:|------|:---:|:---:|
| 第1轮（混合架构） | 感知增强（预测/异常/拓扑） | 🟡 中 | 🔴 大 |
| 第2轮（编排器+黑盒） | 参考算法（RoleAdvisory） | 🟡 中 | 🟡 中 |
| **第3轮（本方案）** | **初步筛选（召回层）** | 🟢 **清晰** | 🟢 **小** |

**演进本质**：黑盒的职责从"提供决策依据"逐步收敛到"过滤噪声、标记候选"，决策权始终保留在白盒。

---

## 三、"召回层 + 精确层"两阶段架构

```
海量原始数据 (日志/流量/告警/事件)
        │
        ▼
┌─────────────────────────────┐
│ 多黑盒阵列 (召回层/Recaller) │  ← 黑盒：宁可错杀不可漏网
│  模型1: 异常流量检测          │     输出: 候选风险信号 + 置信度
│  模型2: 攻击模式识别          │     (不决策，只标记)
│  模型3: 行为基线偏离          │
│  模型N: ...                  │
│  └─ 阵列合并 (投票/并集)      │
└──────────────┬──────────────┘
               │ 候选信号集
               ▼
┌─────────────────────────────┐
│ 白盒仲裁层 (Precisioner)     │  ← 白盒：确定性验证 + 可审计决策
│  白盒规则 → 确定性验证        │     输出: 确定性动作
│  策略引擎 → 响应决策          │
│  定位聚合 → 攻击者定位        │
└─────────────────────────────┘
```

**关键特性**：黑盒阵列只负责"召回"（recall 优先），白盒负责"精确"（precision 优先）。两者职责正交，无耦合。

## 四、对白盒属性的破坏面积

### 4.1 破坏面积评估

| 白盒属性 | 破坏面积 | 说明 |
|------|:---:|------|
| SSAM/Prism 确定性评分 | 🟢 **零** | 黑盒筛选不影响评分公式 |
| 策略引擎确定性响应 | 🟢 零 | 黑盒标记的信号仍需白盒规则二次判断 |
| 定位聚合可解释性 | 🟢 零 | 黑盒筛出候选，白盒归因定位 |
| 审计可追溯性 | 🟢 零 | 黑盒筛选结果仅作审计附注，不进入主体 |
| HMAC 审计一致性 | 🟢 零 | 黑盒不参与签名数据 |

### 4.2 相比前两轮的优势

| 维度 | 第1/2轮 | 第3轮（筛选） |
|------|:---:|:---:|
| 黑盒是否进入决策链 | 是（参考/增强） | **否**（仅预筛） |
| 黑盒输出类型 | 分数/置信度 | 候选信号标记 |
| 白盒是否被迫依赖黑盒 | 部分依赖 | **完全不依赖** |
| 漏报风险 | 低（黑盒辅助） | 🔴 **高**（黑盒是唯一召回源） |

## 五、多黑盒阵列的工程形态

### 5.1 阵列合并策略（借鉴 multi-algo-orchestrator）

| 合并策略 | 语义 | 适用 |
|------|------|------|
| **并集 (Union)** | 任一模型标记即候选 | 召回优先（默认） |
| 交集 (Intersection) | 所有模型一致才候选 | 精确优先 |
| 加权投票 (Weighted Vote) | 按置信度加权 | 平衡 |

**推荐默认：并集** —— 符合"召回层宁可错杀不可漏网"的定位。

### 5.2 阵列的置信度标注

每个黑盒输出必须附带置信度，白盒仲裁时按置信度分级：
- 高置信度 → 白盒快速通道
- 中置信度 → 白盒深度验证
- 低置信度 → 白盒观察（不决策）

### 5.3 与现有架构的接口

| 现有组件 | 对接方式 |
|------|------|
| 多算法编排器 | 黑盒阵列作为 `RoleAdvisory` 批量挂载，新增 `MergeWhiteboxFirst` 隔离 |
| 扩展体系 | 黑盒模型作为 extmgr 外部进程扩展，通过扩展点触发 |
| 事件总线 | 黑盒阵列订阅 `agent.heartbeat`/`adapter.findings`，发布 `recaller.candidates` |

## 六、关键风险（本轮新引入）

### 6.1 漏报风险（最高）

| 风险 | 场景 | 后果 | 缓解 |
|------|------|------|------|
| **R1 单点漏报** | 黑盒阵列是唯一召回源，某个攻击模式未被任何模型识别 | 攻击者完全漏过白盒 | 保留白盒的独立探测通道作为兜底 |
| **R2 模型偏见共振** | 多个黑盒模型用相似数据训练，共性偏见 | 阵列整体漏报某类攻击 | 模型来源/训练数据多样化 |
| **R3 阈值过高** | 阵列置信度阈值设太高 | 漏报低置信度但真实的攻击 | 阈值保守（宁低勿高） |

### 6.2 误报风险（次之）

| 风险 | 后果 | 缓解 |
|------|------|------|
| R4 误报洪泛 | 黑盒阵列并集误报过多 | 白盒资源耗尽 | 置信度分级 + 限流 |
| R5 白盒被噪声淹没 | 候选信号过载 | 白盒漏判真实攻击 | 阵列投票降噪 |

## 七、可行性裁定

**可行，推荐作为主方向。** 理由：

1. **架构定位最优**：黑盒"召回"与白盒"精确"职责正交，边界清晰
2. **破坏面积最小**：黑盒完全不进入决策链，白盒六项属性零破坏
3. **符合安全工程实践**：SIEM/SOAR 的检测层（黑盒 ML）+ 响应层（白盒规则）正是此模式
4. **可渐进落地**：先单黑盒召回，再扩展为阵列；白盒通道始终保留作兜底

### 必须守住的两条红线

| 红线 | 说明 |
|------|------|
| **红线1：黑盒只召回不决策** | 黑盒输出永远是"候选信号"，白盒规则未确认前不得触发任何动作 |
| **红线2：白盒独立兜底** | 即使黑盒阵列全部失效，白盒的独立探测通道（现有 76 扩展点）仍能发现攻击 |

### 落地顺序（风险递增）

1. 🟢 单黑盒召回 + 白盒独立兜底（验证架构）
2. 🟡 多黑盒阵列（并集合并 + 置信度分级）
3. 🟡 加权投票 + 模型多样化（抗偏见共振）

---

## 八、结论

**"多黑盒阵列负责初步信息筛选"是三轮演进中最优的架构定位**，将黑盒职责收敛为"召回层"，白盒保留完整决策权，破坏面积降至零。

与前两轮审计（混合架构红线 + 编排器 RoleAdvisory）的结论**一致且递进**：本轮方案正是"黑盒不直接驱动决策"这条红线的**最纯粹工程实现**——黑盒连"参考"都不做，只做"预筛"。

最大风险从"破坏白盒属性"转移为"**漏报**"（黑盒阵列是唯一召回源时）。缓解手段是保留白盒独立探测通道作兜底，确保"即使黑盒全失效，白盒仍能发现攻击"。
