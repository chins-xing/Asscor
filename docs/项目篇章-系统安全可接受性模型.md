# SSAM 2.0 白皮书（算法篇章）：系统安全可接受性模型

**版本：** 2.0  
**日期：** 2026-05-28  
**状态：** 发布

> **注**：本文档的权威版本现驻留于 [ssam-lib/SSAM-Theory.md](https://github.com/asscor/ssam)（`github.com/asscor/ssam`）。SSAM V2.0 已独立为纯函数式 Go 模块。此处为 ASSCOR 平台同步副本。

## 摘要

系统安全可接受性模型（System Security Acceptability Model，SSAM）2.0 是一种多维度、可计算、可演进的安全评估框架。它通过四个互不重叠的核心能力域——攻击面管理、业务连续性、操作可信度、韧性——与独立边缘修正因子、动态威胁系数及安全态势计算相结合，将系统安全状态量化为一个 0–100 的分数。SSAM V2.0 引入三层语义模型（本征/暴露/威胁），以三个独立风险层的加权平均取代 V1.x 中 ThreatCoeff 与 SPCScore 的单一乘法叠加，消除双重罚分问题。本白皮书系统阐述 SSAM 的理论基础、核心规则、评估方法，并重点介绍韧性维度的增强：可接受沦陷指标（ACI），以及安全态势计算模块（SPC），通过全局漏洞情报与本地资产清单的交叉比对，实现个体化的风险评估。所有参数均可由管理员按场景自定义，实现"定义权归模型，决策权归人"的安全度量实践。

ASSCOR 不替代漏洞扫描器、SIEM 或渗透测试，而是作为上述系统的"安全可接受性"聚合判断层，提供面向业务风险的统一视图。同时，SSAM 已实现与中国等级保护制度（GB/T 22239-2019）的双向映射，可作为等保合规效果的持续性量化验证工具。

## 1. 引言

安全评估长期面临两大困境：合规清单无法应对高级威胁，而红队演练又难以重复度量。ASSCOR 项目旨在提供一种可计算、可演进、可配置的中间道路，让系统管理员像查看健康仪表盘一样，快速掌握当前的安全可接受程度。

SSAM 2.0 的核心创新包括：

- 四核心域互斥设计，消除重复评分
- 边缘因子以乘法修正方式反映高级防护缺失
- 动态威胁系数结合实时情报使评估结果随威胁环境变化
- 管理员完全自定义，权重、阈值、检查项均可按需调整
- 韧性维度强化，新增可接受沦陷指标（ACI），量化"部分失陷后的生存能力"
- 安全态势计算模块（SPC），将全局漏洞情报本地化，为每台主机生成独立的态势修正
- 等级保护制度接入，实现合规要求与安全能力的双向映射
- **三层语义模型（SSAM V2.0 新增）**：以本征（Intrinsic）、暴露（Exposure）、威胁（Threat）三个独立风险层取代单一乘法叠加，消除双重罚分，提升可解释性
- **Formula DSL / AST（SSAM V2.0 新增）**：运行时动态构造评分公式，无需修改代码即可调整层权重和组合方式
- **SSAM IR（SSAM V2.0 新增）**：声明式 JSON 中间表示，便于下游工具链（SIEM、SOC Dashboard、合规审计）消费

## 2. 核心架构

### 2.1 四个互斥核心域

| 核心域 | 核心问题 | 典型检查项 |
|--------|----------|-----------|
| 攻击面管理 | 被动防御面是否最小化？ | 无用服务关闭、非必要端口静默、强认证策略、SSH 安全配置 |
| 业务连续性 | 安全策略是否影响业务运行？ | 关键服务状态、业务端口可达性、资源充裕度、备份机制 |
| 操作可信度 | 配置与操作是否防篡改且可追溯？ | 关键文件权限、审计日志、命令历史防篡改、供应链完整性、强制访问控制 |
| 韧性 | 系统在持续压力与部分失陷后能否保持核心防御？ | 自动封禁精度、内核抗压参数、连接数限制、服务降级策略、可接受沦陷指标 (ACI) |

各域得分范围 0–100，所有检查项互斥，避免同一弱点被重复扣分。

**互斥性声明：** 每项原子检查只归属唯一核心域。例如 SSH 配置（端口、密码策略）仅出现在攻击面管理中；而 SSH 审计日志的完整性则属于操作可信度。评估引擎在加载检查项时会执行冲突检测，确保无交叉。

### 2.2 边缘因子（乘法修正）

某些全局性安全能力无法归属单一域，但缺失时会削弱整体安全水平。这些独立属性以乘法因子形式影响总分：

| 独立属性 | 缺失时因子 | 说明 |
|----------|------------|------|
| 双因素认证缺失 | ×0.85 | 未配置二次认证（EF-002FA） |
| SYN Cookie 未开启 | ×0.75 | 网络层全局防护缺失（EF-SYNCOOKIE） |
| SELinux 未启用 | ×0.80 | 强制访问控制缺失（EF-SELINUX） |
| AppArmor 未启用 | ×0.82 | 强制访问控制缺失（EF-APPARMOR） |
| SIEM 集成缺失 | ×0.90 | 安全事件集中管理缺失（EF-NO-SIEM） |
| IDS/IPS 缺失 | ×0.88 | 入侵检测/防御系统缺失（EF-NO-IDS） |
| 三因素认证未达标 | ×0.82 | 等保四级级联：触发时覆盖 EF-002FA 为 ×0.82（EF-3FA，CascadeOnly） |

> **SSAM 1.3 变更说明：** 供应链校验、自动封禁、资源紧张等项已移入对应核心域检查项（OT-004、RS-003、BC-003），以消除与核心域检查项的重叠。SYN Cookie 仍保留为边缘因子（因其在网络层全局生效）。SELinux/AppArmor、SIEM、IDS/IPS 因其全局防护属性保留为边缘因子。

所有因子数值均可由管理员调整。因子和权重均支持按节点标签/组覆盖，未覆盖者继承全局默认值。

### 2.3 威胁态势系数 μ

通过集成威胁情报（如 OTX、MISP），系统实时计算当前威胁系数 μ，范围 0.60–1.00。默认 1.00，当出现高危漏洞或活跃攻击时自动下调，立即影响所有受管主机的评估结果。

### 2.4 三层语义模型（SSAM V2.0 新增）

SSAM V2.0 的核心架构变更是以三个独立语义层取代 V1.x 中 ThreatCoeff 和 SPCScore 的单一乘法叠加。每个层有独立的含义、输入和计算逻辑：

| 风险层 | 语义 | 输入 | 输出 |
|--------|------|------|------|
| **Intrinsic（本征风险）** | 系统自身的配置安全基线，与外部环境无关 | 核心域加权得分 + 边缘因子连乘 | Intrinsic Score ∈ [0, 100] |
| **Exposure（暴露风险）** | 系统对外暴露的脆弱性面 | SPC P_score、CVE 匹配数量/严重度、端口暴露面 | Exposure Score ∈ [0, 100] |
| **Threat（威胁风险）** | 当前威胁环境的影响 | CTI μ 系数、KEV 在野利用、威胁组织活跃度 | Threat Score ∈ [0, 100] |

**三层模型的优势：**

1. **消除双重罚分**：V1.x 中，一个低 SPC P_score 同时被乘以 μ，形成"系统有漏洞 + 外部有威胁"的复合惩罚，导致评分对单一维度的波动过度敏感。V2.0 的三层加权平均确保各维度独立评估后公正组合。
2. **提升可解释性**：管理员可清晰看到"配置扣了多少分（Intrinsic）"、"漏洞扣了多少分（Exposure）"、"当前威胁环境扣了多少分（Threat）"，便于针对性修复。
3. **灵活权重配置**：管理员可通过 config.ini 配置层权重（默认 50/30/20），不同场景下聚焦不同层。等保合规场景可提高 Intrinsic 权重，重保期间可提高 Threat 权重。
4. **向后兼容**：`ssam_v1.2` 公式继续可用，旧版配置无需修改。

**V2.0 公式（SSAMV20Formula）：**

```
layer_intrinsic = (Σ(S_i × W_i) / ΣW_i) × ΠM_j
layer_exposure  = 100 - f(SPC_P_score, CVE_count, CVE_severity)
layer_threat    = 100 - g(μ, KEV_status, ThreatActor_activity)

SSAM_final = Σ(layer_k × layer_weight_k) / Σlayer_weight_k
```

三层默认权重：Intrinsic 50、Exposure 30、Threat 20，总和 100。可通过 `[v2_layer_weights]` 配置段调整。

**Formula DSL / AST（SSAM V2.0 新增）：**

V2.0 支持通过 Formula DSL 在运行时动态构造评分公式，无需修改代码。管理员可通过配置文件直接编写公式表达式：

```ini
[v2_formula]
expression = "intrinsic * 0.5 + exposure * 0.3 + threat * 0.2"
```

或使用更复杂的组合：

```ini
[v2_formula]
expression = "round(min(intrinsic, 100) * 0.5 + max(exposure, 0) * 0.3 + sqrt(threat * 100) * 0.2) / 2"
```

公式表达式由 `ParseFormula()` 编译为 AST，由 `EvaluateFormula()` 求值，性能等同硬编码公式。

**SSAM IR JSON 中间表示（SSAM V2.0 新增）：**

评估结果可导出为声明式 JSON 结构（SSAMIR），便于下游工具链消费：

```json
{
  "ssamir_version": "1.0",
  "host_id": "prod-web-01",
  "formula_id": "ssam_v2.0",
  "final_score": { "value": 72.35, "acceptable": false },
  "layers": {
    "intrinsic": { "score": 82.0, "weight": 0.50 },
    "exposure":  { "score": 60.0, "weight": 0.30 },
    "threat":    { "score": 70.0, "weight": 0.20 }
  },
  "domain_scores": { ... },
  "edge_factors": [ ... ]
}
```

详细接口规范与接入指南请参阅 [SSAM接口规范与接入指南](SSAM接口规范与接入指南.md)。

## 3. 评估公式

SSAM 1.3 的最终评估值由核心域加权得分、边缘因子修正、威胁态势系数及安全态势计算修正共同决定。SPC 1.3 采用平方和开方（√∑Penalty²）替代线性求和，防止大量低危 CVE 过早触底。

$$
SSAM_{final} = \left( \frac{\sum_{i=1}^{4} (S_i \times W_i)}{\sum_{i=1}^{4} W_i} \right) \times \prod_{j=1}^{m} M_j \times \mu \times P_{score}
$$

其中：

- $S_i$：第 i 个核心域得分（0–100）
- $W_i$：该域权重，默认值：攻击面管理 35，业务连续性 25，操作可信度 25，韧性 15
  - **权重之和推荐为 100；若非 100，引擎自动按 $\sum W_i$ 归一化，确保评分结果不受权重配置误差影响**
- $M_j$：第 j 个独立边缘因子（0.0–1.0）
- $\mu$：威胁态势系数（0.6–1.0）
- $P_{score}$：由 SPC 输出的个体化态势分数修正因子（0.60–1.00，详见第 5 章）

> **规划中**：SPC 可选输出的核心域权重临时偏移 $P_{weight}(i)$（总和为 0），用于在检测到某域防护与当前威胁极不匹配时动态调整权重聚焦。该偏移由 SPC 模块生成但尚未集成到评分公式，将在后续版本启用。

可接受阈值 T 由管理员设定（默认 80）。当 $SSAM_{final} \geq T$ 时，系统安全状态判为可接受。

## 4. 韧性指标增强：可接受沦陷指标（ACI）

传统的韧性评估关注系统抵御攻击的能力，但现实中"完全不被攻破"难以保证。SSAM 1.3 在韧性核心域中引入可接受沦陷指标（ACI），用于衡量：当系统的某一部分已被攻破时，能否将损害控制在可接受范围内，并维持核心业务的运行。

ACI 与抗打击韧性指标互为补充：前者衡量"破防后"，后者衡量"破防前"。两者不重叠、不重复扣分。

### 4.1 ACI 的设计目标

- **隔离能力**：受影响组件能否被快速隔离，阻止横向移动
- **最小权限有效性**：攻击者获得的权限是否被限制在极小的范围内
- **数据保护**：敏感数据是否加密、备份是否离线且不可篡改
- **恢复能力**：从检测到沦陷到恢复正常服务的时间（MTTR）
- **监控留存**：攻击者能否轻易清除入侵痕迹

### 4.2 ACI 的评估假设

ACI 评估默认假设攻击者已获得目标组件的基础访问权限（如 Web 服务用户、低权账户），并以此为前提衡量损害扩散范围。该假设提供了可比较的工程化基线。

### 4.3 ACI 评估项与计分

ACI 各项的扣分值直接在韧性域百分制内加减，扣至 0 分为止。

| 检查项 | 评估方法 | 默认扣分 |
|--------|----------|----------|
| 网络分段验证 | 检查 VLAN/防火墙策略，确认关键业务段是否隔离 | -15 |
| 本地管理员密码唯一性 | 是否部署 LAPS 或类似机制 | -10 |
| 离线备份完整性 | 验证最新备份可恢复且未被加密勒索 | -20 |
| 端点检测响应 (EDR) 部署 | 检查 EDR 是否运行并可检测凭证转储等行为 | -10 |
| 审计日志远程实时备份 | 日志是否发送到独立于被管主机的系统 | -10 |
| 应用程序白名单 | 是否限制可执行文件来源 | -10 |
| 数据防泄露 (DLP) 措施 | 敏感数据出口是否受控 | -5 |
| 恢复能力验证 | 检查系统恢复能力（ReaR/Relax-and-Recover）和 MTTR 相关配置 | -10 |

每项扣分值可由管理员自定义配置。

> **ACI 与 BC 备份检查的互斥边界：** 业务连续性域 `BC-005/006` 检查"备份策略存在与执行"（备份机制是否配置并运行），ACI 的"离线备份完整性"检查"备份在沦陷假定下是否仍有效"（备份是否可恢复、未被加密勒索）。若备份完全不存在，BC 和 ACI 均应扣分（两者从不同维度评估同一缺失，不算重复扣分）；若备份存在但未加密，仅影响 ACI；若备份策略完整且离线备份可恢复但未定期执行，仅 BC 扣分。社区贡献检查项时须遵循此边界。

## 5. 安全态势计算模块（SPC）

### 5.1 设计目标

SSAM 1.3 引入安全态势计算模块（Security Posture Calculator，SPC），解决"全局漏洞情报"与"单台主机实际风险"之间的鸿沟。SPC 通过持续追踪全球权威漏洞库，结合本地资产清单，为每台受管主机输出个体化的态势修正向量。

SPC 的核心设计原则：

- **本地化优先**：同一 CVE 在不同主机上的影响因资产角色、网络位置、已有控制措施而异
- **时间衰减**：漏洞威胁随发布天数递减，但不会完全消失（最低衰减至 0.3）
- **多源融合**：综合 CVSS 严重度、EPSS 利用预测、CISA KEV 在野利用状态三个独立维度
- **可解释性**：每个 $P_{score}$ 的组成均可追溯到具体的 CVE 和匹配条件
- **下限保护**：$P_{score}$ 最低 0.60，防止情报噪声"杀死"主机评分

### 5.2 数据源体系

SPC 构建了分层数据源体系，从全球情报到本地资产形成完整的信息链路：

**一级数据源（基础漏洞数据库）：**

| 数据源 | 覆盖范围 | 更新频率 | 接入方式 |
|--------|----------|----------|----------|
| NVD（National Vulnerability Database） | 全球 CVE，CVSS 评分，CPE 匹配 | 每日 | NVD API 2.0 / JSON Feed |
| CNNVD（中国国家信息安全漏洞库） | 中文漏洞描述，国产软件覆盖 | 每日 | CNNVD API |
| CNVD（中国国家信息安全漏洞共享平台） | 国内厂商漏洞，工控漏洞 | 实时 | 数据订阅 |
| OSCAL（NIST） | 标准化控制评估与漏洞报告格式 | 按需 | XML / JSON / YAML 解析 |

OSCAL（Open Security Controls Assessment Language，NIST SP 800-53 系列）在此发挥关键的标准化作用：它提供结构化的安全评估结果表达格式，使不同来源的漏洞数据能够以统一的 XML/JSON/YAML 结构流转。SPC 利用 OSCAL 的 `assessment-results` 模型导入第三方扫描器的输出，避免为每种扫描器编写独立的解析器。

**二级数据源（威胁上下文）：**

| 数据源 | 说明 | 应用 |
|--------|------|------|
| EPSS（Exploit Prediction Scoring System） | 漏洞在未来 30 天内被利用的概率（0–1） | 占 Impact 权重 50% |
| CISA KEV（Known Exploited Vulnerabilities） | 已知在野利用的漏洞目录 | 占 Impact 权重 30% |
| MITRE ATT&CK | 攻击技术、战术、威胁组织知识库 | 战术到检查项映射，技术覆盖度分析 |
| MISP Threat Intelligence | 社区驱动的威胁情报平台 | 威胁组织特征、IOC 模式、Galaxy 聚类 |

**三级数据源（本地资产上下文）：**

- Agent 采集：已安装软件包及版本（RPM/DPKG）、运行服务及监听端口、内核版本与 sysctl 参数、网络拓扑位置及段信息
- 配置数据：主机角色标签（web-server、database、bastion 等）、所属业务系统、等保定级级别
- 历史数据：历史漏洞修补记录、平均修补时间（MTTP）、历史安全事件记录

### 5.3 态势修正向量

SPC 为每台主机输出修正向量 $\vec{P_h} = (P_{score}, P_{weight}, P_{action})$：

- $P_{score}$：态势分数修正因子（0.60–1.00），作为乘数进入最终公式
- $P_{weight}$：核心域权重临时偏移（总和为 0）
- $P_{action}$：建议响应动作（如 isolate_host、notify_admin）

**$P_{weight}$ 的生成逻辑：**

当 SPC 检测到某一核心域的防护与当前威胁极不匹配时，会生成权重偏移向量。例如检测到主机存在 3 个以上网络暴露型高危 CVE 时，攻击面管理域权重临时 +5，业务连续性域权重临时 −5，使评估更聚焦于攻击面问题；该偏移为诊断性辅助，不影响最终评分的计算逻辑一致性。

权重偏移仅影响核心域加权求和部分，与态势分数修正 $P_{score}$ 可同时生效，两者作用于最终公式的不同位置。

**$P_{action}$ 的触发条件与分级：**

| 级别 | 触发条件 | 建议动作 | 自动化 |
|------|----------|----------|--------|
| ACTION_NONE | $P_{score} \geq 0.95$ | 无需动作 | — |
| ACTION_WARN | $0.85 \leq P_{score} < 0.95$ | 通知管理员关注 | 消息推送 |
| ACTION_PATCH | $0.75 \leq P_{score} < 0.85$ | 建议打补丁，提供修补清单 | 生成修复脚本 |
| ACTION_PRIORITY | $0.65 \leq P_{score} < 0.75$ | 优先处置，标记为紧急 | 自动加入变更窗口 |
| ACTION_ISOLATE | $P_{score} < 0.65$ | 建议临时隔离主机 | 生成 iptables/nft 规则 |

### 5.4 计算公式

$P_{score}$ 计算：

$$P_{score}(h) = \max\left(0.60,\; 1.00 - \sqrt{\sum_{i=1}^{n} Penalty_i^2}\right)$$

其中每个 CVE 的罚分为：

$$Penalty_i = Impact(CVE_i) \times LocalFactor(CVE_i, h) \times TimeWindow(CVE_i)$$

多 CVE 罚分叠加采用平方和开方（√∑Penalty²）替代线性求和，防止大量低危 CVE 过早触底。

**Impact（漏洞影响度）子公式：**

$$Impact = 0.20 \cdot f_{cvss} + 0.50 \cdot f_{epss} + 0.30 \cdot f_{kev}$$

其中各子因子的定义：

$$f_{cvss} = \min\left(1.0, \frac{CVSS\_Score}{10.0}\right)$$

$$f_{epss} = \min\left(1.0, \frac{-\ln(1 - EPSS\_Score)}{5}\right)$$

$$f_{kev} = \begin{cases} 1.0 & \text{若在 CISA KEV 目录中} \\ 0.3 & \text{若存在公开 PoC 但不在 KEV} \\ 0.0 & \text{其他情况} \end{cases}$$

EPSS 因子采用对数缩放，使高利用概率的 CVE 获得显著更高的权重。例如 EPSS=0.01 时 $f_{epss}≈0.002$，EPSS=0.5 时 $f_{epss}≈0.139$，EPSS=0.9 时 $f_{epss}≈0.460$。相比线性缩放（`EPSS×10`），对数缩放在高概率区间提供更好的区分度。权重分配（0.20/0.50/0.30）体现了"预测性利用概率 > 已知在野利用 > 理论严重度"的设计偏好。

**LocalFactor（本地化匹配因子）子公式：**

$$LocalFactor = MatchType \times ExposureLevel \times ControlFactor$$

| 子因子 | 取值 | 条件 |
|--------|------|------|
| MatchType | 1.0 | 软件版本精确匹配 |
|  | 0.7 | 软件族匹配，版本范围包含 |
|  | 0.3 | 仅 CPE 厂商/产品匹配 |
|  | 0.0 | 无匹配 |
| ExposureLevel | 1.0 | 受影响端口直接暴露于公网 |
|  | 0.7 | 受影响端口在 DMZ 区域 |
|  | 0.4 | 受影响端口仅内网可访问 |
|  | 0.1 | 受影响端口仅本地回环 |
| ControlFactor | 1.0 | 无补偿控制措施 |
|  | 0.5 | 存在部分补偿控制（如 WAF、IPS 规则覆盖） |
|  | 0.2 | 存在有效补偿控制（如已配置虚拟补丁） |

**TimeWindow（时间衰减）子公式：**

$$TimeWindow = \max(0.3, 1.0 - \frac{days}{90})$$

其中 $days$ = 漏洞公开日期距今天数。90 天内线性衰减至 0.3，超过 90 天保持 0.3 的基线（永不归零，因为未修补的老旧漏洞在特定条件下仍可能被利用）。

$P_{score}$ 下限为 0.60，防止 SPC 单方面"杀死"主机评分。

### 5.5 SPC 数据流水线架构

SPC 采用事件驱动的流水线架构，各阶段异步解耦：

```
┌─────────────────────────────────────────────────────────────────────┐
│                        SPC Data Pipeline                            │
├──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│ 采集层   │→│ 标准化层  │→│ 匹配引擎  │→│ 计算引擎  │→│ 输出层   │ │
│ Collector│  │Normalizer │  │ Matcher  │  │Calculator│  │ Exporter │ │
├──────────┤  ├──────────┤  ├──────────┤  ├──────────┤  ├──────────┤ │
│·NVD API  │  │·OSCAL     │  │·CPE匹配  │  │·Impact   │  │·P_vector │ │
│·MISP API │  │  Transform│  │·版本比对 │  │·Local    │  │·事件通知 │ │
│·NVD Feeds│  │·JSON      │  │·拓扑感知 │  │·Time     │  │·Dashboard│ │
│·Agent    │  │  Normalize│  │·补偿控制 │  │·Superpos │  │·μKernel  │ │
│ 上报     │  │           │  │  判断    │  │          │  │  分发    │ │
└──────────┘  └──────────┘  └──────────┘  └──────────┘  └──────────┘ │
└─────────────────────────────────────────────────────────────────────┘
```

**采集层（Collector）：**

采集层负责从所有数据源拉取数据，支持以下接入模式：

- **NVD API v2.0**：通过 RESTful API 以 CVE 为粒度增量同步，默认同步间隔 6 小时，支持 CPE 名称匹配搜索
- **MISP REST API**：通过 PyMISP 或原生 HTTP 客户端拉取威胁事件、属性、Galaxy 标签，同步间隔可配置（默认 1 小时），支持按标签过滤（如 `workflow:state="complete"`）
- **Arrowhead Agent 上报**：Agent 按心跳周期（默认 2s）上报本地软件清单，包含 package_name、version、vendor、CPE 信息
- **OSCAL 文档导入**：支持导入 OSCAL XML/JSON/YAML 格式的第三方漏洞评估报告，解析 `assessment-results` 模型中的 `finding` 节点，提取 CVE 编号与受影响资产

**标准化层（Normalizer）：**

标准化层将所有异构数据统一为内部规范格式。这一层的关键设计是采用 OSCAL 作为数据交换的标准参照系：

```
原始数据 → OSCAL 内部格式 → SPC 统一漏洞模型
```

OSCAL 的核心优势：它由 NIST 维护，与 NVD/CVE 生态天然对齐；其 `system-security-plan`、`assessment-plan`、`assessment-results` 三个核心模型覆盖了从系统描述到评估结果的完整生命周期。SPC 使用以下 OSCAL 模型映射：

| OSCAL 模型 | SPC 映射 | 说明 |
|------------|----------|------|
| `system-security-plan` | 主机资产清单（components/inventory-items） | 系统组件、软件、端口 |
| `assessment-results / findings` | 漏洞发现（CVE + 影响组件） | 每个 finding 对应一个 CVE 实例 |
| `assessment-results / observations` | 检查项结果（pass/fail） | 与 ASSCOR 检查项映射 |
| `assessment-results / risks` | 风险条目（risk-status, characterization） | 输入 Impact 计算的原始材料 |

标准化后的统一漏洞模型（SPC Vulnerability Record）包含：

```yaml
vuln_record:
  cve_id: "CVE-2024-1234"
  description: "..."
  cvss_score: 9.8
  cvss_vector: "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H"
  epss_score: 0.72
  epss_percentile: 0.95
  in_kev: true
  date_published: "2024-01-15"
  affected_cpes: ["cpe:2.3:a:vendor:product:1.0:*:*:*:*:*:*:*"]
  attck_techniques: ["T1190", "T1210"]
  misp_galaxy_tags: ["misp-galaxy:mitre-attck-pattern"]
  oscal_finding_uuid: "a1b2c3d4-..."
```

**匹配引擎（Matcher）：**

匹配引擎将标准化漏洞记录与本地主机资产清单进行交叉比对：

1. **CPE 匹配**：漏洞的 affected_cpes 与主机的 installed_cpes 精确比对
2. **版本范围分析**：基于 CPE 版本区间判断主机软件版本是否在受影响范围内
3. **拓扑上下文**：结合主机网络位置（公网/DMZ/内网/本地）判定 ExposureLevel
4. **补偿控制评估**：查询主机是否有已部署的 WAF 规则、IPS 签名、应用白名单等补偿措施，决定 ControlFactor

**计算引擎（Calculator）：**

计算引擎执行 §5.4 的完整公式，处理多 CVE 叠加效应。核心算法：

```
FOR each host h:
    sum_of_squares = 0
    FOR each matched CVE_i in matched_cves(h):
        impact = 0.20 * f_cvss(CVE_i) + 0.50 * f_epss(CVE_i) + 0.30 * f_kev(CVE_i)
        local = MatchType(CVE_i, h) * ExposureLevel(CVE_i, h) * ControlFactor(CVE_i, h)
        time = max(0.3, 1.0 - days_since(CVE_i) / 90)
        penalty = impact * local * time
        sum_of_squares += penalty * penalty
    total_penalty = sqrt(sum_of_squares)
    P_score = max(0.60, 1.00 - total_penalty)
    P_weight = generate_weight_shift(matched_cves(h))
    P_action = classify_action(P_score)
    emit_vector(h, P_score, P_weight, P_action)
```

**输出层（Exporter）：**

输出层将修正向量分发到各个消费端：

- **μKernel**：通过 Event Bus 发布 `spc:vector:updated` 事件，内核获取最新 $P_{score}$ 后更新全局 $SSAM_{final}$
- **Dashboard**：通过 WebSocket 推送态势变化，实时展示各主机 SPC 分数和影响最大的 CVE
- **Agent 反馈**：通过 $P_{action}$ 触发 Agent 端的自动化响应（如生成 iptables 隔离规则）
- **告警通道**：ACTION_PATCH 及以上级别的建议动作通过邮件/钉钉/Webhook 推送给管理员

### 5.6 MISP 威胁情报集成架构

SSAM 1.3 通过 MISP（Malware Information Sharing Platform，当前稳定版本 2.5.x）接入社区威胁情报，增强 SPC 的威胁上下文能力。

**MISP 核心概念与 SPC 的映射：**

MISP 是一个开源威胁情报平台，其核心数据模型包括事件（Event）、属性（Attribute）、对象（Object）、Galaxy 和 Taxonomy。SPC 利用以下 MISP 特性：

| MISP 概念 | SPC 应用 | 说明 |
|-----------|----------|------|
| Event（事件） | 威胁事件批次 | 一个 MISP Event 可映射为一组相关的 CVE 或攻击活动 |
| Attribute（属性） | IOC 提取 | 从 Event 中提取 IP、域名、文件哈希、CVE 编号等 IOC |
| Galaxy Cluster | 威胁组织识别 | 利用 MISP Galaxy（集成 MITRE ATT&CK、威胁组织、勒索软件等）进行战术和技术关联 |
| Taxonomy | 分类标记 | 用于对威胁事件进行分类（如 TLP、PAP、workflow 状态） |
| Tag | 自动标签 | MISP 的标签系统可自动为 CVE 打上 ATT&CK 技术标签 |

**MISP REST API 集成流程：**

1. **事件同步**：通过 `/events/index` 端点获取近期事件列表，支持按 `date_from`、`tags`、`org` 过滤。SPC 的重点关注标签包括 `tlp:white`（可共享）、`workflow:state="complete"`（已完成分析）

2. **ATT&CK Galaxy 解析**：MISP Galaxy 库包含 MITRE ATT&CK 的完整技术、战术和威胁组织数据（以 `misp-galaxy:mitre-attck-pattern`、`misp-galaxy:mitre-intrusion-set` 等形式存在）。SPC 解析 Galaxy 标签，将 CVE 事件关联到具体的 ATT&CK 技术和威胁组织

3. **STIX 2 互操作**：MISP 原生支持 STIX 2.x 导入/导出。SPC 可消费 STIX 2 格式的威胁情报（Indicator、Campaign、Threat Actor SDO），实现与 SOC 系统的互操作

4. **IOC 提取与加权**：从 MISP 事件属性中提取以下类型的 IOC：
   - `type: vulnerability` → CVE 编号（直接匹配）
   - `type: exploit` → 关联到对应 CVE
   - `type: pattern-in-file` → 文件哈希（用于供应链关联）
   - `type: ip-dst` / `type: domain` → 网络 IOC（用于 ExposureLevel 评估）

5. **威胁组织关联加权**：当 MISP 事件中的 Galaxy 标签指向已知 APT 组织时，SPC 对关联的 CVE 额外乘以 1.2 的组织威胁系数，使 $Impact$ 计算反映威胁组织活跃度

**MISP Taxonomy 在 SPC 中的应用：**

SPC 利用 MISP 的 Taxonomy 系统进行情报质量分级：

| Taxonomy | 取值 | SPC 处理 |
|----------|------|----------|
| `tlp` | white/green/amber/red | 仅处理 tlp:white 和 tlp:green 的情报 |
| `admiralty-scale` | 1–6（来源可靠性） | 可靠性 < 3 的情报降低权重 50% |
| `workflow` | todo/incomplete/complete | 仅处理 complete 状态的事件 |
| `estimative-language` | likelihood 估计 | 用于 TimeWindow 的额外加权 |

ASSCOR 的 SPC 模块内置了基于标准 `net/http` 的 MISP 客户端（不依赖 PyMISP，保持零外部依赖），核心 API 调用：

### 5.7 MITRE ATT&CK 攻击矩阵映射

SPC 集成 MITRE ATT&CK（当前版本 v19）知识库，将攻击技术与 SSAM 检查项建立双向映射关系，使漏洞风险评估从"是否有漏洞"升级为"漏洞可被哪种攻击技术利用"。

**ATT&CK 14 战术概览与 SSAM 覆盖：**

MITRE ATT&CK Enterprise 矩阵包含以下 14 个战术（Tactic），每个战术下包含若干具体技术（Technique）。SPC 将 ATT&CK 技术与 SSAM 四个核心域及检查项进行关联映射：

| ATT&CK 战术 | 战术 ID | 主要关联核心域 | 典型技术示例 | SSAM 覆盖度 |
|-------------|---------|---------------|-------------|-------------|
| 侦察（Reconnaissance） | TA0043 | 攻击面管理 | T1595 主动扫描、T1592 收集目标信息 | 间接（Agent 可检测扫描行为） |
| 资源开发（Resource Development） | TA0042 | 攻击面管理 | T1587 开发能力、T1588 获取能力 | 间接（供应链完整性检查） |
| 初始访问（Initial Access） | TA0001 | 攻击面管理 | T1190 漏洞利用、T1133 外部远程服务 | 直接（端口扫描、服务审计） |
| 执行（Execution） | TA0002 | 操作可信度 | T1059 命令执行、T1203 客户端漏洞利用 | 直接（命令历史审计、白名单检查） |
| 持久化（Persistence） | TA0003 | 操作可信度 | T1547 启动项、T1053 计划任务 | 直接（关键文件权限、启动项审计） |
| 权限提升（Privilege Escalation） | TA0004 | 操作可信度 | T1068 漏洞提权、T1548 滥用提权机制 | 直接（SUID 审计、内核参数检查） |
| 防御规避（Defense Evasion） | TA0005 | 操作可信度、韧性 | T1562 禁用安全工具、T1070 清除痕迹 | 直接（审计日志防篡改、EDR 状态检查） |
| 凭证访问（Credential Access） | TA0006 | 操作可信度 | T1003 凭证转储、T1110 暴力破解 | 直接（PAM 配置、密码策略、SSH 加固） |
| 发现（Discovery） | TA0007 | 韧性 | T1082 系统信息发现、T1018 远程系统发现 | 间接（异常行为基线检测） |
| 横向移动（Lateral Movement） | TA0008 | 韧性 | T1021 远程服务、T1210 漏洞利用 | 直接（网络分段、横向移动检测） |
| 收集（Collection） | TA0009 | 韧性 | T1005 本地数据收集、T1560 数据压缩 | 间接（DLP 措施、异常流量检测） |
| 命令与控制（Command and Control） | TA0011 | 韧性 | T1071 应用层协议、T1573 加密信道 | 直接（出站连接限制、DNS 监控） |
| 窃取（Exfiltration） | TA0010 | 韧性、业务连续性 | T1041 C2 信道窃取、T1048 替代协议窃取 | 直接（DLP、出口流量审计） |
| 影响（Impact） | TA0040 | 业务连续性 | T1486 数据加密勒索、T1485 数据破坏 | 直接（离线备份完整性、ACI 检查） |

**技术到检查项映射方法：**

SPC 采用三层映射策略，将 ATT&CK 技术（Technique）关联到 SSAM 具体检查项：

1. **直接映射**：攻击技术直接对应已有的 SSAM 检查项。例如 T1190（漏洞利用公共应用）→ 攻击面管理的端口扫描与服务审计检查（AS-001、AS-002）

2. **间接映射**：攻击技术通过防护措施对应检查项。例如 T1059（命令和脚本解释器）→ 操作可信度的命令历史防篡改检查（OT-001）和应用程序白名单检查（OT-010）

3. **关联映射**：攻击技术通过多个检查项的组合覆盖。例如 T1003（OS 凭证转储）→ 操作可信度的 PAM 配置检查（OT-011）+ 关键文件权限检查（OT-002）+ 韧性域的 EDR 部署检查（RS-006）

**ATT&CK 子技术对 SPC 计算的影响：**

ATT&CK 的子技术（Sub-technique）提供了更精细的攻击面描述。SPC 在计算 $Impact$ 时，会额外考虑：

$$Impact_{enhanced} = Impact_{base} \times (1 + 0.1 \times N_{sub\_tech})$$

其中 $N_{sub\_tech}$ 是某个 CVE 已知可被利用的 ATT&CK 子技术数量。例如，一个漏洞若可被用于 3 种不同的子技术攻击路径，其 $Impact$ 会额外增加 30%，反映该漏洞在实际攻击中的多样化利用能力。

**ATT&CK 技术覆盖热力图：**

ASSCOR 管理系统可生成技术覆盖热力图，横轴为 14 个战术，纵轴为受管主机或主机组。每个格子表示该主机对该战术下攻击技术的防护覆盖度（0–100%），由相关检查项的通过率计算得出。这为安全管理员提供了直观的盲区识别能力。

热力图计算公式：

$$Coverage(tactic) = \frac{\sum_{check \in mapped(tactic)} PassRate(check)}{|mapped(tactic)|}$$

### 5.8 多 CVE 叠加计算示例

以下通过一个完整示例展示 SPC 的计算流程。

**场景设定：**

主机 `web-prod-01`，角色为 Web 服务器，部署在 DMZ 区域，等保三级。操作系统 Ubuntu 22.04 LTS，运行 Nginx 1.24.0、OpenSSL 3.0.2、PHP 8.1。

当前日期：2026-05-13。本地匹配到以下 3 个 CVE：

| CVE | CVSS | EPSS | KEV | 公开日期 | 匹配类型 | 暴露级别 | 补偿控制 |
|-----|------|------|-----|----------|----------|----------|----------|
| CVE-2024-1234（OpenSSL RCE） | 9.8 | 0.72 | 是 | 2026-04-15 | 精确匹配 | DMZ (0.7) | 无 (1.0) |
| CVE-2024-5678（Nginx HTTP/3 DoS） | 7.5 | 0.15 | 否 | 2026-03-20 | 精确匹配 | DMZ (0.7) | WAF 规则 (0.5) |
| CVE-2024-9012（PHP 信息泄漏） | 5.3 | 0.03 | 否 | 2025-12-01 | 版本范围包含 (0.7) | 仅内网 (0.4) | 无 (1.0) |

**逐步计算：**

**CVE-2024-1234：**

- $f_{cvss} = \min(1.0, 9.8/10.0) = 0.98$
- $f_{epss} = \min(1.0, 0.72 \times 10) = \min(1.0, 7.2) = 1.00$
- $f_{kev} = 1.0$（在 CISA KEV 目录中）
- $Impact = 0.20 \times 0.98 + 0.50 \times 1.00 + 0.30 \times 1.00 = 0.196 + 0.500 + 0.300 = 0.996$
- $MatchType = 1.0$（精确匹配），$ExposureLevel = 0.7$（DMZ），$ControlFactor = 1.0$（无补偿）
- $LocalFactor = 1.0 \times 0.7 \times 1.0 = 0.70$
- $days = 28$，$TimeWindow = \max(0.3, 1.0 - 28/90) = \max(0.3, 0.689) = 0.689$
- $Penalty_1 = 0.996 \times 0.70 \times 0.689 = 0.480$

**CVE-2024-5678：**

- $f_{cvss} = \min(1.0, 7.5/10.0) = 0.75$
- $f_{epss} = \min(1.0, 0.15 \times 10) = \min(1.0, 1.5) = 1.00$
- $f_{kev} = 0.0$（不在 KEV 且无公开 PoC）
- $Impact = 0.20 \times 0.75 + 0.50 \times 1.00 + 0.30 \times 0.0 = 0.150 + 0.500 + 0.000 = 0.650$
- $MatchType = 1.0$，$ExposureLevel = 0.7$（DMZ），$ControlFactor = 0.5$（WAF 补偿）
- $LocalFactor = 1.0 \times 0.7 \times 0.5 = 0.35$
- $days = 54$，$TimeWindow = \max(0.3, 1.0 - 54/90) = \max(0.3, 0.400) = 0.400$
- $Penalty_2 = 0.650 \times 0.35 \times 0.400 = 0.091$

**CVE-2024-9012：**

- $f_{cvss} = \min(1.0, 5.3/10.0) = 0.53$
- $f_{epss} = \min(1.0, 0.03 \times 10) = \min(1.0, 0.3) = 0.30$
- $f_{kev} = 0.0$
- $Impact = 0.20 \times 0.53 + 0.50 \times 0.30 + 0.30 \times 0.0 = 0.106 + 0.150 + 0.000 = 0.256$
- $MatchType = 0.7$（版本范围包含），$ExposureLevel = 0.4$（仅内网），$ControlFactor = 1.0$
- $LocalFactor = 0.7 \times 0.4 \times 1.0 = 0.28$
- $days = 163$，$TimeWindow = \max(0.3, 1.0 - 163/90) = \max(0.3, -0.811) = 0.300$（触底）
- $Penalty_3 = 0.256 \times 0.28 \times 0.300 = 0.022$

**最终结果：**

> **SPC 1.3 叠加衰减：** SPC 1.3 采用平方和开方（√∑Penalty²）替代线性求和，防止大量低危 CVE 过早触底 0.60，保持高风险区分度。

$$\sqrt{\sum Penalties^2} = \sqrt{0.480^2 + 0.091^2 + 0.022^2} = \sqrt{0.2304 + 0.0083 + 0.0005} = \sqrt{0.2392} = 0.489$$

$$P_{score}(web\text{-}prod\text{-}01) = \max(0.60,\ 1.00 - 0.489) = \max(0.60,\ 0.511) = 0.600$$

由于 $P_{score} < 0.65$，触发 `ACTION_ISOLATE` 级别的建议动作。

**分析解读：**

- CVE-2024-1234 是绝对主导贡献者（占 96.3% 的平方罚分），因为它同时具备高 CVSS、高 EPSS、KEV 在野利用和短时间窗口四项高危特征
- CVE-2024-5678 虽然 CVSS 不低，但 WAF 补偿控制和时间衰减使其平方贡献几乎可忽略（3.5%）
- CVE-2024-9012 由于仅影响内网、版本匹配较弱且时间衰减触底，平方贡献近乎为零（0.2%）
- 平方和开方叠加方式使高影响力 CVE 的权重更加突出，低危漏洞不会快速累积至触底
- 主机评分触底（0.60），说明在 DMZ 区域运行的未修补高危漏洞组合已构成严重风险

**权重偏移计算（$P_{weight}$）：**

> **注意**：$P_{weight}$ 为规划中功能，当前版本尚未集成到评分公式。以下计算仅作设计说明。

该主机检测到关键漏洞主要集中在网络暴露层面，SPC 生成权重偏移：

$$P_{weight} = (attck\_surface: +5,\ business\_continuity: -3,\ operation\_trust: 0,\ resilience: -2)$$

总和为 0，符合约束。攻击面管理权重从 35 临时升至 40，业务连续性从 25 临时降至 22，韧性从 15 临时降至 13。这使评估更聚焦于攻击面问题，而对业务运行和韧性的关注暂时降低。

**最终公式代入：**

假设该主机的四个核心域得分分别为 $S = (60, 85, 90, 70)$，所有边缘因子 $M_j = 1.0$（无缺失），威胁系数 $\mu = 0.85$：

$$SSAM_{final} = \left( \frac{60 \times 35 + 85 \times 25 + 90 \times 25 + 70 \times 15}{35+25+25+15} \right) \times 1.0 \times 0.85 \times 0.600$$

$$= \left( \frac{2100 + 2125 + 2250 + 1050}{100} \right) \times 0.85 \times 0.600$$

$$= 75.25 \times 0.85 \times 0.600 = 38.38$$

低于默认阈值 80，系统判定为安全不可接受，应立即采取补救措施。

## 6. APT 攻击分析与检测

高级持续性威胁（Advanced Persistent Threat，APT）是当前企业安全面临的最严峻挑战之一。与普通攻击不同，APT 攻击具有高度组织化、长期潜伏、多阶段递进的特征，传统安全评估往往难以覆盖其全生命周期。SSAM 1.3 通过整合 MITRE ATT&CK、MISP 威胁情报与 SPC 模块，构建了一套面向 APT 攻击的量化分析框架，覆盖攻击建模、检测盲区识别、组织行为画像及预测性风险评估。

### 6.1 APT 杀伤链模型与 SSAM 映射

APT 攻击通常遵循分阶段的杀伤链（Kill Chain）模型。基于洛克希德·马丁传统杀伤链的扩展，结合 ATT&CK 知识库，SSAM 定义了适配防御者视角的 APT 阶段性模型：

│TA0043   │     │TA0042   │     │TA0001   │     │TA0001   │

                    APT 杀伤链全生命周期                    │

┌─────────┐     ┌─────────┐     ┌─────────┐     ┌─────────┐
│数据窃取  │◀────│横向扩散  │◀────│持久控制  │◀────│权限提升  │

### 6.2 ATT&CK 技术覆盖度分析

ASSCOR 将自身检查项映射到 ATT&CK 14 个战术，计算每个战术的技术覆盖度，识别检测和防护盲区。

**技术覆盖度计算模型：**

对于每个战术，ASSCOR 计算两个维度的覆盖度：

1. **检测覆盖度（Detection Coverage，$DC$）**：有对应的检查项能够检测或防御的技术子项比例

$$DC(tactic) = \frac{|Techniques\_Covered(tactic)|}{|Techniques\_Total(tactic)|}$$

2. **防护覆盖度（Prevention Coverage，$PC$）**：有对应的加固/防护措施能够阻止的技术子项比例

$$PC(tactic) = \frac{|Techniques\_Prevented(tactic)|}{|Techniques\_Total(tactic)|}$$

3. **综合覆盖度（Composite Coverage，$CC$）**：

$$CC(tactic) = 0.4 \cdot DC(tactic) + 0.6 \cdot PC(tactic)$$

防护权重大于检测权重（0.6 > 0.4），体现"预防优于检测"的安全原则。

### 6.3 APT 组织检测模型

ASSCOR 利用 MISP Galaxy 聚类中的威胁组织知识图谱，构建基于 ATT&CK 技术的 APT 组织行为匹配模型。

**威胁组织行为画像：**

MISP Galaxy 的 `misp-galaxy:threat-actor` 聚类收录了全球已知 APT 组织的技术画像。每个组织关联了一组其惯用的 ATT&CK 技术。ASSCOR 从 MISP 同步这些数据，构建组织行为特征向量：

$$Profile(G) = \{(T_i, w_i) \mid T_i \in Techniques(G),\ w_i = usage\_frequency(T_i, G)\}$$

其中 $w_i$ 是该组织在公开报告中使用技术 $T_i$ 的频率权重。

**典型 APT 组织的 ATT&CK 技术选择差异：**

不同 APT 组织表现出不同的技术偏好（基于 MITRE ATT&CK Groups 数据）：

| 组织 | 别名 | 典型目标 | 核心技术偏好 | 特征战术阶段 | 惯用 CVE 类型 |
|------|------|----------|-------------|-------------|--------------|
| APT29 | Cozy Bear | 政府、外交 | T1566 钓鱼、T1071 C2 协议、T1003 凭证转储 | TA0001→TA0006→TA0010 | 邮件客户端 RCE、认证绕过 |
| APT41 | Wicked Spider | 多行业 | T1190 漏洞利用、T1059 脚本执行、T1021 远程服务 | TA0001→TA0002→TA0008 | Web 服务器 RCE、供应链漏洞 |
| Lazarus | HIDDEN COBRA | 金融、政府 | T1566 鱼叉、T1203 客户端利用、T1486 数据加密 | TA0001→TA0002→TA0040 | 浏览器漏洞、文档编辑漏洞 |
| APT28 | Fancy Bear | 政府、军事 | T1566 钓鱼、T1133 外部远程服务、T1110 暴力破解 | TA0001→TA0003→TA0006 | VPN 漏洞、认证系统漏洞 |
| FIN7 | Carbanak | 零售、金融 | T1566 钓鱼、T1055 进程注入、T1210 漏洞利用 | TA0001→TA0004→TA0008 | 办公软件漏洞、RDP 漏洞 |

**组织相似度匹配算法：**

对于受管网络中检测到的安全事件序列 $E = \{e_1, e_2, ..., e_n\}$，ASSCOR 计算其与已知 APT 组织的行为相似度：

$$Sim(E, G) = \frac{|Techniques(E) \cap Techniques(G)|}{|Techniques(E) \cup Techniques(G)|} \times \sum_{T \in Techniques(E) \cap Techniques(G)} w(T, G)$$

该算法同时考虑技术集合的重叠度（Jaccard 系数）和重叠技术的权重累加，避免仅凭少量高权重技术匹配就误判为特定组织。

当 $Sim(E, G) > 0.6$ 且有至少 5 项技术匹配时，ASSCOR 发出 APT 组织预警，并提供该组织的完整 ATT&CK 技术画像作为防御参考。

**MISP 组织画像数据同步机制：**

ASSCOR 定期（默认 24 小时）从 MISP Galaxy 同步威胁组织数据：

```
MISP Galaxy Endpoint:
GET /galaxies/index
  ?namespace=misp
  &name=threat-actor
  → 获取威胁组织列表及关联的 ATT&CK 技术

GET /galaxy_clusters/view/
  ?galaxy_id=<threat-actor-galaxy-id>
  → 获取特定组织的技术画像
  → 解析 Galaxy Cluster 的 meta 字段中的 ATT&CK 技术映射
```

### 6.4 预测性风险评估

SSAM 1.3 在 SPC 的个体化评分基础上，引入了预测性风险评估（Predictive Risk Assessment，PRA），通过分析 APT 组织的技术使用模式，预测尚未发生但可能发生的攻击路径。

**攻击路径推理引擎：**

基于 ATT&CK 知识库中技术之间的关联关系（例如 T1190 漏洞利用公共应用后通常跟随 T1059 命令执行 或 T1003 凭证转储），ASSCOR 项目构建技术转移概率矩阵：

$$Trans(T_a, T_b) = P(T_b \mid T_a) = \frac{Count(T_a \rightarrow T_b\ in\ reported\ attacks)}{Count(T_a\ occurrences)}$$

转移概率矩阵从 MITRE ATT&CK 的 "Procedure Examples" 数据中自动提取，并结合 MISP 事件的实际攻击链数据进行补充。

**预测风险分数：**

对于已检测到攻击活动（或漏洞）的主机，预测其未来可能遭受的攻击路径风险：

$$Risk_{predict}(h) = \max_{path \in Paths(h)} \prod_{(T_a, T_b) \in path} Trans(T_a, T_b)$$

其中 $Paths(h)$ 是从当前检测到的技术出发，遍历转移矩阵可达的攻击路径集合。预测风险分数反映了攻击者沿着已知攻击模式推进的可能性和危害程度。

**融合到 SSAM 评分：**

预测风险通过扩展的威胁系数间接影响 $SSAM_{final}$：

$$\mu_{enhanced} = \mu \times \max(0.75,\ 1.0 - Risk_{predict}(h) \times 0.25)$$

当主机存在高概率攻击路径时（$Risk_{predict}$ 较高），增强版威胁系数 $\mu_{enhanced}$ 会更低，从而更显著地拉低最终评分。该修正的上限为 0.75，避免预测不确定性过度影响当前评分。

**预测性修复建议：**

PRA 不仅提供预警，还为每台主机生成"预测性加固建议"——在攻击发生前，针对高转移概率的下一步技术，建议提前部署相应的防御措施。例如：

- 检测到主机存在可被 T1190（漏洞利用）利用的未修补漏洞 → 建议同时加固 T1059（限制脚本执行）和 T1003（加固凭证存储）的防护
- 检测到可疑的 T1018（远程系统发现）行为 → 建议提前收紧 T1021（远程服务）的访问控制，阻断横向移动路径

### 6.5 SPC 与 APT 分析的联动

APT 分析模块与 SPC 的联动体现在以下三个层面：

**层面 1：威胁情报增强 $Impact$ 计算**

当 MISP 数据表明某个 CVE 是特定 APT 组织的常用武器化漏洞时，SPC 的 $Impact$ 计算自动增强：

$$Impact_{apt} = Impact_{base} \times (1 + 0.2 \times N_{apt\_groups\_using\_this\_cve})$$

例如，CVE-2024-1234 被 APT29 和 Lazarus 两个组织同时使用，其 $Impact$ 额外增加 40%（$0.2 \times 2 = 0.4$），反映该漏洞的战略价值。

**层面 2：ATT&CK 覆盖缺口自动告警**

当 ASSCOR 检测到某一主机的业务角色与已知 APT 组织优先攻击的目标重合（如邮件服务器对标 APT29），而该主机在该组织惯用技术的覆盖度不足时，自动生成覆盖缺口告警：

```
ALERT: web-prod-01 对标 APT41 攻击模式，
       当前覆盖 62%（阈值 75%），缺少：
       - T1059.001 PowerShell 执行监控
       - T1021.001 RDP 连接审计
       - T1505.003 Web Shell 检测
```

**层面 3：杀伤链完整性评估**

ASSCOR 为每台主机计算 APT 杀伤链各阶段的防御完整性，生成阶段防御评分：

$$KillChainScore(h) = \frac{\sum_{stage \in KillChain} min(100, \sum_{check \in stage} PassScore(check))}{|KillChain|}$$

当某一阶段得分低于阈值（默认 60 分）时，标记该阶段为"脆弱阶段"，提示管理员重点加固。

**跨模块数据流：**

```
┌─────────────┐    ┌──────────────┐    ┌──────────────┐
│ MISP Galaxy │───▶│ APT 分析引擎 │───▶│ SPC 计算引擎│
│ 威胁组织画像 │    │·行为匹配     │    │·Impact 增强 │
│             │    │·技术转移矩阵 │    │·P_score 修正│
└─────────────┘    │·杀伤链评估   │    │·P_action 建议│
                   └──────────────┘    └──────┬───────┘
                                              │
                   ┌──────────────┐           │
                   │  μKernel     │◀──────────┘
                   │  Event Bus   │  spc:vector:updated
                   │  评分更新    │  apt:threat:matched
                   └──────────────┘
```

## 7. 等级保护制度接入

SSAM 1.3 已与 GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》（等保 2.0）建立映射关系。四个核心域覆盖等保"安全通信网络"、"安全区域边界"、"安全计算环境"和"安全管理中心"中可自动化评估的部分，物理安全、人员管理等人工审查项不在此列。

### 7.1 等保等级与 SSAM 阈值联动

| 等保等级 | 推荐 SSAM 阈值 | 适用场景 |
|----------|----------------|----------|
| 二级 | 65 | 一般信息系统 |
| 三级 | 80（默认） | 重要系统 |
| 四级及以上 | 90 | 关键基础设施 |

### 7.2 等保控制点映射原则

以等保三级安全计算环境为例，从身份鉴别、访问控制、安全审计、入侵防范、恶意代码防范、数据保护、备份恢复、剩余信息保护等方面推导出 53 项 SSAM 检查项，每一项均可追溯到具体的等保标准条款。所有映射详情请见第二篇章：等保检查项映射手册。

### 7.3 双向验证

ASSCOR 项目评估结果可与等保测评报告交叉验证：若等保三级通过而 SSAM < 80，可能存在配置漂移或防护未持续生效；反之若 SSAM ≥ 80 而等保未通过，则说明部分人工审查项需重点整改。

ASSCOR 项目现已具备结合 §6 中 APT 分析的能力：当等保合规通过、但 ASSCOR 项目的 APT 杀伤链评估仍存在高风险阶段时，提示安全管理员"合规≠安全"，需在等保基线之上叠加面向高级威胁的纵深防御。

## 8. 动态扩展与社区驱动

ASSCOR 内置攻击向量插件槽（AVD），每个 AVD 定义为 {ID, 域, 检测逻辑, 分值, 紧急标记}。管理员或社区可编写 AVD 注册到引擎，使模型随威胁演进持续扩展。

社区驱动的威胁数据同步包括：

- **ATT&CK 技术更新**：MITRE ATT&CK 每年发布 2–3 个主要版本，增删技术子项及子技术。ASSCOR 通过自动化 ATT&CK STIX 2 数据同步，保持技术映射表的最新状态
- **MISP Galaxy 同步**：当社区发现新 APT 组织或更新现有组织技术画像时，ASSCOR 自动拉取最新的 Galaxy 聚类数据
- **OSCAL 扩展**：当新漏洞评估格式（如 SARIF、CycloneDX VEX）出现时，可通过 OSCAL 转换层快速适配

## 10. 与 ASSCOR μKernel 的联动

ASSCOR μKernel 是风险评估与指令分发中心，采用微内核 + Agent 架构，通过 mTLS 加密的 gRPC 通信。Agent 负责本地检查执行与状态上报，内核汇聚计算并自动下发修复指令，实现"评估→诊断→修复"闭环。

SPC 与 APT 分析模块均以插件形式注册到 μKernel 的扩展点，通过 Event Bus 与内核及其他模块交互。APT 模块产生的威胁匹配事件和预测风险数据，经由 `apt:threat:matched` 和 `apt:risk:predicted` 事件通道发送到 SPC 和策略引擎，形成跨模块的协作评估。

## 11. 总结

SSAM 1.3 提供了一套严谨且可进化的安全可接受性度量标准。四个核心域与边缘因子、威胁系数、SPC 态势修正共同形成完整的风险评估体系。通过引入 APT 攻击分析，ASSCOR 项目进一步扩展了其检测维度：从基于 MITRE ATT&CK 的技术覆盖度评估，到基于 MISP 的组织行为画像匹配，再到基于杀伤链的阶段性防御完整性检验——形成了一条从"当前漏洞"到"未来攻击"的预测性风险链路。

引入等保映射后，ASSCOR 项目既是对抗高级威胁的战术工具，也是衡量合规持续有效性的战略仪表盘。它不仅回答"系统安全吗"，更回答"在当下威胁环境中，我们的安全程度是否可以被接受，以及潜在的高级威胁可能从何处突破"。

## 12. 已知局限与后续工作

- ACI 基于假设攻击者已获基础权限，未覆盖所有攻陷场景
- SPC 精度依赖本地资产清单完整性和情报源质量
- 模型不评估物理安全、社会工程学等非技术向量
- 大规模环境下的检查项互斥验证和性能优化尚待持续完善
- APT 组织行为画像依赖公开情报，对未公开组织行为（零日攻击、定制工具）不具备覆盖能力
- 攻击路径预测精度受 ATT&CK 技术转移矩阵的完备性和时效性制约
- 杀伤链评估中的阶段权重和阈值需要针对不同行业/场景进行实证校准
