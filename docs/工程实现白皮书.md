# SSAM 2.0 工程实现白皮书（ASSCOR 项目）

**版本：** 1.7
**日期：** 2026-05-28  
**状态：** 发布  
**配套理论文档：** SSAM 2.0 白皮书（第一篇章）、等级保护检查项映射手册（第二篇章）、监管委员会章程（第三篇章）

## 摘要

本文是 SSAM 2.0（系统安全可接受性模型）的 ASSCOR 项目工程实现规范，详细描述分布式评估系统的技术选型、架构设计、模块划分、通信协议、数据模型、安全机制、构建部署与扩展策略。系统采用 Go 语言实现的微内核 + Agent 架构，通过自研 JSONRPC 与 mTLS 实现高性能、安全的双向通信。所有设计遵循低耦合、可扩展、零外部依赖（核心）原则，方便社区贡献与跨平台部署。

### SSAM V2.0 项目拆分

自 SSAM V2.0 起，核心评分算法已从 ASSCOR 框架中完全独立为纯函数式库 [github.com/asscor/ssam](https://github.com/asscor/ssam)（位于 `ssam-lib/`）。ssam-lib 是一个零外部依赖的纯 Go 函数库——无 goroutine、无锁、无 I/O、无 RPC、无插件。ASSCOR 平台通过 `internal/ssam/` 薄适配层委托调用 ssam-lib，两者通过标准化接口松耦合协作：

```
ASSCOR Platform (插件式分布式平台)
    │
    ├── internal/ssam/    (薄适配层：adapter.go + defaults.go)
    │       │
    │       └── 委托给 → ssam-lib/  (github.com/asscor/ssam)
    │                        ├── ssam.go         — Engine 核心、钩子、校验
    │                        ├── types.go        — V1.x DTO (向后兼容)
    │                        ├── types_v2.go     — V2.0 三层模型类型
    │                        ├── formulas.go     — V1.x 公式 (ssam_v1.2)
    │                        ├── formulas_v2.go  — SSAMV20Formula
    │                        ├── ir.go           — SSAM IR 导出
    │                        ├── ast.go          — Formula DSL / AST
    │                        └── formulas_ast.go — AST 公式实现
    │
    └── internal/kernel/  (插件总线、gRPC、DI、SPC、ATT&CK...)
```

ASSCOR——希腊神话中的百眼巨人，全视、警惕、永不闭目。这个名字本身就是项目的隐喻：持续监控每一台主机的安全状态，不放过任何一个弱点。眼睛是项目的灵魂元素，也是 ASSCOR 最核心的意象。

## 1. 技术选型

| 层次 | 选用技术 | 选择理由 |
|------|----------|----------|
| 编程语言 | Go 1.21+ | 静态编译，零依赖分发，原生并发，跨平台支持 |
| 通信协议 | JSONRPC (自研兼容层) + gRPC (原生) | 双协议栈：JSONRPC 零外部依赖，gRPC 原生协议支持高性能场景；均支持 mTLS |
| 传输安全 | mTLS (双向认证) | 确保内核与 Agent 间身份认证与加密，防止中间人攻击 |
| 配置格式 | INI (通过自定义解析器) | 简单易读，管理员可直接编辑，无需特殊工具 |
| 并发控制 | Goroutine + Channel + Semaphore | 利用 Go 原生并发实现检查项并行执行，信号量限制并发数 |
| 数据存储 | 内存缓存 + JSONL 持久化 + SPC 磁盘缓存 | 评估结果实时计算，缓存5分钟；SPC CVE 缓存启动加载/退出保存；历史数据 JSONL 按日轮转 |
| 前端仪表板 | 待定 (建议 React/Vue + Go API 网关) | 初期提供 CLI 输出与 JSON 报告，Web UI 作为社区贡献模块 |
| 容器化 | Docker + Kubernetes (可选) | 内核可容器化部署，Agent 推荐直接运行于宿主机 |

## 2. 总体架构

系统采用微内核 + Agent 分布式架构，内核作为中央安全大脑，Agent 作为分布在各业务主机的执行探头。

## 3. 模块详细设计

### 3.1 内核模块

#### 3.1.1 评估引擎

- **职责**：加载检查项，并发执行评估，计算核心域得分，应用边缘因子、威胁系数、SPC 修正，生成最终 SSAM 分数。
- **关键接口**：Evaluate(hostID) -> AssessmentResult
- **并发模型**：使用 Goroutine 池，最大并发 10，通过 channel 信号量控制。
- **缓存**：结果缓存 5 分钟，由读写锁保护。
- **SSAM 1.3 内置冲突检测**：引擎在 Bootstrap 启动阶段加载所有检查项后，执行互斥性冲突检测——按检查项 ID 与核心域归属建立索引，扫描是否存在同一原子检查被分配至多个核心域的情况。若检测到冲突（如 SYN Cookie 同时出现在边缘因子和韧性域），引擎拒绝启动并输出冲突详情（冲突检查项 ID、涉及的核心域列表），强制修复后方可继续。这确保了 §2.1 互斥性声明在工程层面的强制执行。

#### 3.1.2 策略管理器

- **职责**：读取配置阈值，根据分数区间生成自动化动作。
- **状态机**：OK (≥阈值) → Warning (≥阈值-10) → Critical (≥阈值-30) → Isolated (<阈值-30)
- **动作映射**：notify_admin, increase_assessment, block_ip, disable_service, isolate_host。
- **v1.5 修复**：原实现使用嵌套 switch 导致阈值区间重叠（外层设为 `HostIsolated` 后内层又覆盖为 `HostWarning`），现合并为单一互斥 switch，按分数从高到低依次判断，确保每个分数只命中一个状态。

#### 3.1.3 安全态势计算器 (SPC)

- **职责**：从 NVD、EPSS、CISA KEV 拉取漏洞情报，与本地资产清单比对，输出 $P_{score}$、$P_{weight}$、$P_{action}$。
- **数据源**：REST API 或本地镜像，定期更新（1h）。
- **本地化因子**：MatchType, ExposureLevel, ControlFactor。
- **SPC 1.3 叠加衰减**：多 CVE 罚分叠加采用平方和开方（$\sqrt{\sum Penalty^2}$）替代线性求和。防止大量低危 CVE 过早将 $P_{score}$ 触底至 0.60，使高影响力 CVE 的权重更加突出，保持高风险区分度。实现上，Calculator 引擎在遍历 matched_cves 时累加各 Penalty 的平方值，最终执行 `math.Sqrt(sumOfSquares)` 得到叠加罚分。
- **v1.5 修复**：
  - **CVE 匹配逻辑**：原实现使用 CVE ID（如 `CVE-2023-1234`）匹配包名，导致数字子串误匹配（如"2023"包）；且短包名（<2 字符）易产生误匹配。现移除 CVE ID 匹配路径，仅使用 Description 文本匹配，并过滤长度 <2 的包名。
  - **EPSS 缩放**：原 EPSS 因子使用线性缩放（`EPSS*10`），无法准确反映利用概率的量级差异。现改为对数缩放 `-log(1-EPSS)/5`，使高 EPSS 值的惩罚更显著，低 EPSS 值的影响更温和。

#### 3.1.4 威胁情报管理器

- **职责**：接入 OTX、MISP 等情报源，计算全局威胁系数 μ。
- **接口**：GetThreatCoefficient() -> float64
- **v1.5 修复**：原 `ReportThreat` 方法仅递增 `activeThreats` 计数，未区分威胁严重级别。现新增 `severityWeight` 函数，按威胁级别加权计算（critical=4, high=3, medium=2, low=1），使威胁系数更准确反映实际风险等级。

#### 3.1.5 指令下发器

- **职责**：将策略管理器生成的动作转化为 Agent 可执行的命令，通过 gRPC 下发，管理重试与超时。
- **签名**：HMAC-SHA256 对命令签名，Agent 验签。
- **v1.5 修复**：原 HMAC 签名仅包含 `cmdID` 和 `action`，未包含 `params`，存在参数篡改风险。现修改 `sign` 方法，按 key 排序后加入所有参数值，Agent 端同步更新验证逻辑，确保命令完整性。
- **HMAC 密钥管理**：密钥元数据包含创建时间、过期时间、SHA-256 哈希；自动轮换周期 90 天；密钥文件权限 `0600`；Agent 启动时若未配置 HMAC 密钥即发出 SECURITY ALERT 告警，运行时拒绝所有远程命令。

#### 3.1.6 日志收集器

- **职责**：接收 Agent 推送的日志流，写入本地或远程日志存储。
- **存储**：仅追加文件，或转发至 SIEM。
- **v1.5 修复**：
  - **日志注入防护**：原 `entry.Message` 含换行符可注入伪造日志条目。现新增 `sanitizeLogField` 函数，将 `\n` 和 `\r` 替换为空格，确保每条日志条目占一行。
  - **数据落盘保障**：原写入后未调用 `Sync()`，进程崩溃可能丢失最近数据。现写入成功后立即调用 `m.writer.Sync()`，确保数据持久化到磁盘。

#### 3.1.7 心跳监控器

- **职责**：跟踪每个 Agent 的最后心跳时间，超时 (默认 60s) 触发失联告警。

### 3.2 Agent 模块

#### 3.2.1 状态采集器

- **职责**：执行 ASSCOR 定义的检查项，生成 CheckResult 列表。
- **检查项实现**：基于 Go 系统调用、文件读取、命令执行。例如：
  - AS-001 检测不必要的服务：解析 systemd 或 /etc/init.d
  - OT-001 文件权限：os.Stat 获取文件 mode
  - RS-005 SYN Cookie：读取 /proc/sys/net/ipv4/tcp_syncookies
- **扩展性**：允许加载外部 Lua 脚本或 WebAssembly 插件（未来）。

#### 3.2.2 指令执行器

- **职责**：接收内核命令，映射到本地操作（如调用 iptables、systemctl、ufw）。
- **安全限制**：白名单命令集，禁止执行任意 shell 脚本。

#### 3.2.3 安全通信代理

- **职责**：管理 gRPC 连接、mTLS 证书、心跳定时器、日志流上传。
- **证书管理**：首次启动生成 CSR，管理员在内核批准后签发证书。后续自动轮换。
- **心跳机制**：使用 `time.Timer` 替代 `time.Ticker`，防止 `runChecks()` 耗时导致的心跳堆积触发连续错误重连。
- **TCP 读取**：使用 `bufio.Reader.ReadBytes('\n')` 按行读取响应，解决 TCP 半包导致的 JSON 解析失败。

## 4. 通信协议与接口定义

### 4.1 Protobuf 服务定义

```protobuf
syntax = "proto3";
package ASSCOR;

service KernelService {
  rpc Register(RegisterRequest) returns (RegisterResponse);
  rpc Heartbeat(HeartbeatRequest) returns (HeartbeatResponse);
}

service AgentService {
  rpc GetSnapshot(SnapshotRequest) returns (SnapshotResponse);
  rpc ExecuteCommand(CommandRequest) returns (CommandResponse);
  rpc StreamLogs(stream LogEntry) returns (Ack);
}

message RegisterRequest {
  string host_id = 1;
  string hostname = 2;
  string version = 3;
}

message RegisterResponse {
  bool accepted = 1;
  string session_id = 2;
  string ca_certificate = 3; // 用于 Agent 验证内核
}

message HeartbeatRequest {
  string host_id = 1;
  string session_id = 2;
  AssessmentResult result = 3; // 嵌入式评估结果，减少 RPC 次数
}

message HeartbeatResponse {
  bool ok = 1;
  double threat_coefficient = 2;
  repeated Command pending_commands = 3;
  AssessmentResult assessment_result = 4; // 评估结果（仅当携带检查结果时返回）
}

message AssessmentResult {
  double final_score = 1;
  bool acceptable = 2;
  map<string, double> domain_scores = 3;
  repeated CheckResult checks = 4;
  map<string, double> edge_factors = 5;   // 边缘因子详情
  double threat_coefficient = 6;           // 威胁系数 μ
  double spc_score = 7;                    // SPC 态势修正因子 P_score
}

message CheckResult {
  string check_id = 1;
  string domain = 2;
  bool passed = 3;
  double delta = 4;
  string detail = 5;
}

message Command {
  string command_id = 1;
  string command = 2;            // 如 "block_ip"
  map<string, string> params = 3;
  string signature = 4;          // HMAC 签名
}

message CommandResponse {
  string command_id = 1;
  bool success = 2;
  string output = 3;
}
```

### 4.2 安全通信流程

1. Agent 启动，生成密钥对和 CSR。
2. 调用 Register，内核验证主机 ID 是否白名单（或管理员审批）。
3. 内核签发 Agent 证书，返回 CA 证书。
4. Agent 与内核建立 mTLS 连接，后续 RPC 均在此连接上进行。
5. Agent 定期（如 5s）发送 Heartbeat，携带最新评估快照。内核返回待执行命令列表。
6. 内核调用 ExecuteCommand 下发指令，Agent 执行后返回结果。
7. Agent 可选调用 StreamLogs 推送实时日志。

### 5.4 数据持久化与存储架构

SSAM 1.3 的数据存储（ASSCOR 实现）采用**内存优先 + 惰性持久化**策略，以"零外部数据库依赖"为核心理念，所有持久化格式均为人类可读的 JSON 行或 INI 文本，确保灾难恢复场景下可直接用文本编辑器抢救数据。

#### 5.4.1 存储分层架构

```
┌──────────────────────────────────────────────────┐
│              热数据层 (L0 — 内存)                    │
│  sync.RWMutex 保护                                  │
│  ├── results map[hostID]*AssessmentResult           │
│  ├── agents  sync.Map[hostID]*AgentRecord           │
│  ├── cveCache []SPCCVEScore                        │
│  └── config  map[string]string                     │
│                                                     │
│  策略: 每次评估更新；读取无锁竞争；5min TTL           │
├──────────────────────────────────────────────────┤
│              温数据层 (L1 — 本地文件)                 │
│  ├── data/assessments.jsonl   (评估结果日志)         │
│  ├── data/agents.jsonl        (Agent 注册记录)       │
│  ├── data/audit.jsonl         (审计日志, 只追加)      │
│  └── data/commands.jsonl      (指令下发记录)         │
│                                                     │
│  策略: 每 30s 批量刷盘；只追加不修改；按天自动切割     │
├──────────────────────────────────────────────────┤
│              冷数据层 (L2 — 可选 SQLite)              │
│  └── data/ASSCOR.db                                 │
│                                                     │
│  策略: 历史趋势分析、合规审计、跨主机关联查询          │
└──────────────────────────────────────────────────┘
```

#### 5.4.2 存储介质选型

| 存储层 | 介质 | 格式 | 选型理由 |
|--------|------|------|----------|
| L0 热数据 | 进程内存 | Go 原生 map/struct | 纳秒级读取，评估计算必须零 I/O 延迟 |
| L1 温数据 | 本地磁盘 | JSONL（每行一条 JSON） | 人类可读，逐行追加无需锁文件，`tail -f` 可实时监控 |
| L2 冷数据 | 本地磁盘 / NFS | SQLite | 嵌入式关系查询，无独立数据库进程，符合"零外部依赖"原则 |
| 审计日志 | 本地磁盘 + 远程 syslog | 只追加文本 | 防篡改要求，不可删除，不可修改 |

**JSONL vs 其他格式对比：**

| 特性 | JSONL | SQLite | 二进制 (Protobuf) |
|------|-------|--------|-------------------|
| 人类可读性 | ★★★ | ★★☆ (需sqlite3客户端) | ★☆☆ |
| 写入性能 | ★★★ (追加写入) | ★★☆ (B-tree 写入) | ★★★ |
| 查询能力 | ★☆☆ (仅流式扫描) | ★★★ (完整 SQL) | ★☆☆ |
| 文件损坏恢复 | ★★★ (逐行恢复) | ★★☆ (需要修复工具) | ★☆☆ |
| 跨平台兼容 | ★★★ | ★★★ | ★★★ |
| 备份友好度 | ★★★ (普通文件同步) | ★★☆ (需要一致性快照) | ★★★ |

#### 5.4.4 持久化核心实现

```go
type PersistenceManager struct {
    mu          sync.Mutex
    dataDir     string
    writers     map[string]*jsonlWriter
    flushTicker *time.Ticker
    done        chan struct{}
}

type jsonlWriter struct {
    mu      sync.Mutex
    file    *os.File
    path    string
    day     int  // 当前文件对应日期，用于自动切割
}

func NewPersistenceManager(dataDir string) *PersistenceManager {
    pm := &PersistenceManager{
        dataDir:     dataDir,
        writers:     make(map[string]*jsonlWriter),
        flushTicker: time.NewTicker(30 * time.Second),
        done:        make(chan struct{}),
    }
    go pm.flushLoop()
    return pm
}

func (pm *PersistenceManager) Append(dataset string, record interface{}) error {
    writer, err := pm.getWriter(dataset)
    if err != nil {
        return fmt.Errorf("persist %s: %w", dataset, err)
    }

    data, err := json.Marshal(record)
    if err != nil {
        return fmt.Errorf("marshal: %w", err)
    }

    writer.mu.Lock()
    defer writer.mu.Unlock()

    // 自动按天切割日志文件
    today := time.Now().YearDay()
    if writer.day != today && writer.day != 0 {
        writer.file.Close()
        writer.file = nil
    }

    if writer.file == nil {
        fname := fmt.Sprintf("%s-%s.jsonl", dataset, time.Now().Format("20060102"))
        f, err := os.OpenFile(filepath.Join(pm.dataDir, fname),
            os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0644)
        if err != nil {
            return err
        }
        writer.file = f
        writer.day = today
        writer.path = fname
    }

    _, err = writer.file.Write(append(data, '\n'))
    return err
}

func (pm *PersistenceManager) flushLoop() {
    for {
        select {
        case <-pm.flushTicker.C:
            pm.flushAll()
        case <-pm.done:
            pm.flushAll()
            return
        }
    }
}

func (pm *PersistenceManager) flushAll() {
    pm.mu.Lock()
    defer pm.mu.Unlock()
    for _, w := range pm.writers {
        w.mu.Lock()
        if w.file != nil {
            w.file.Sync()
        }
        w.mu.Unlock()
    }
}

func (pm *PersistenceManager) Close() {
    close(pm.done)
    pm.flushTicker.Stop()
    pm.flushAll()
    for _, w := range pm.writers {
        w.mu.Lock()
        if w.file != nil {
            w.file.Close()
        }
        w.mu.Unlock()
    }
}
```

### 6.2 并发量限制策略

#### 6.2.1 评估并发池设计

检查项执行是 ASSCOR 最核心的计算密集型任务。每个检查项可能因执行系统命令而产生 I/O 等待，无限制地启动 Goroutine 会导致系统资源耗尽。

**并发量计算依据：**

| 参数 | 值 | 依据 |
|------|-----|------|
| 最大并发检查项数 | 10 | 经验值：平衡 CPU 利用率与 I/O 等待 |
| 单检查项超时 | 10s | `context.WithTimeout`，防止命令卡死 |
| 心跳触发间隔 | 5s（Agent → 内核） | 评估频率上限 |
| 评估缓存 TTL | 5min | 同主机 5 分钟内不重复评估 |

**v1.5 修复 — WorkerPool goroutine 泄漏**：原实现中，任务超时后启动的排空 goroutine 未加入 `WaitGroup`，导致 `Shutdown()` 无法等待所有 goroutine 退出。现排空 goroutine 调用 `p.wg.Add(1)` 和 `defer p.wg.Done()`，并绑定 `p.ctx.Done()` 作为退出信号，确保 `Shutdown()` 能正确等待所有 goroutine 结束。

**Goroutine 池核心实现：**

```go
type WorkerPool struct {
    semaphore chan struct{}
    ctx       context.Context
    cancel    context.CancelFunc
    wg        sync.WaitGroup
}

func NewWorkerPool(maxConcurrency int) *WorkerPool {
    ctx, cancel := context.WithCancel(context.Background())
    return &WorkerPool{
        semaphore: make(chan struct{}, maxConcurrency),
        ctx:       ctx,
        cancel:    cancel,
    }
}

func (p *WorkerPool) Submit(task func() error) {
    select {
    case p.semaphore <- struct{}{}:
        p.wg.Add(1)
        go func() {
            defer p.wg.Done()
            defer func() { <-p.semaphore }()
            if err := task(); err != nil {
                log.Printf("worker: task error: %v", err)
            }
        }()
    case <-p.ctx.Done():
        return
    }
}

func (p *WorkerPool) Wait() {
    p.wg.Wait()
}

func (p *WorkerPool) Shutdown() {
    p.cancel()
    p.Wait()
}

func (p *WorkerPool) ActiveWorkers() int {
    return len(p.semaphore)
}

func (p *WorkerPool) QueueDepth() int {
    return cap(p.semaphore) - len(p.semaphore)
}
```

### 6.3 资源竞争处理机制

#### 6.3.1 共享状态保护矩阵

| 数据结构 | 并发访问模式 | 保护机制 | 竞争风险 |
|----------|-------------|----------|----------|
| `results map[hostID]*AssessmentResult` | 多读单写（评估更新） | `sync.RWMutex` | 低 — 读多写少 |
| `agents map[hostID]*AgentRecord` | 多读多写（心跳频繁更新） | `sync.Map` | 中 — 高并发心跳 |
| `cveCache []SPCCVEScore` | 定时更新 + 评估读取 | `sync.RWMutex` | 低 — 每小时更新一次 |
| `pendingCmds map[hostID]map[cmdID]*Command` | 单写多读（Commander 独占） | `sync.Mutex` | 低 — 单 goroutine 写入 |
| `config map[string]string` | 启动时写入 + 运行时只读 | 启动后不可变（immutable after boot） | 无 |
| `subscribe map[topic][]subscriber` | 多写（注册期）+ 多读（运行时） | `sync.RWMutex` | 低 — 注册期在启动阶段 |

#### 6.3.2 锁升级策略（避免死锁）

```
锁获取顺序（全局约定，违反即为 Bug）：
  1. Kernel.mu          (最外层)
  2. 模块级 mu           (如 Assessor.mu, Policy.mu)
  3. 数据结构级 mu       (如 Container.mu, Bus.mu)
  4. 文件/网络 I/O      (最内层，禁止持锁等待 I/O)

原则:
  • 禁止持锁调用外部模块方法（防止隐式锁依赖）
  • 禁止持锁执行 I/O 操作（超时不确定）
  • RWMutex.RLock 可重入；RWMutex.Lock 不可重入
  • 所有 ctx 超时由调用方设置，不在持锁状态下等待 ctx
```

```go
// 每个 goroutine 必须遵循的模式：
func safeGoroutine(ctx context.Context, fn func() error) {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("goroutine panic recovered: %v\n%s", r, debug.Stack())
            metrics.Increment("goroutine.panics")
        }
    }()

    done := make(chan error, 1)
    go func() {
        done <- fn()
    }()

    select {
    case err := <-done:
        if err != nil {
            log.Printf("goroutine error: %v", err)
        }
    case <-ctx.Done():
        log.Printf("goroutine cancelled: %v", ctx.Err())
        // goroutine 中运行的 fn 必须自身响应 ctx.Done()
    }
}
```

```go
type HeartbeatPipeline struct {
    inbound chan *apiv1.HeartbeatRequest
    dedup   map[string]time.Time
    mu      sync.Mutex
}

func NewHeartbeatPipeline() *HeartbeatPipeline {
    hp := &HeartbeatPipeline{
        inbound: make(chan *apiv1.HeartbeatRequest, 256),
        dedup:   make(map[string]time.Time),
    }
    go hp.consume()
    return hp
}

func (hp *HeartbeatPipeline) Submit(req *apiv1.HeartbeatRequest) {
    select {
    case hp.inbound <- req:
    default:
        metrics.Increment("heartbeat.dropped")
        log.Printf("heartbeat pipeline full, dropping request from %s", req.HostId)
    }
}

func (hp *HeartbeatPipeline) consume() {
    ticker := time.NewTicker(1 * time.Second)
    defer ticker.Stop()

    var batch []*apiv1.HeartbeatRequest

    for {
        select {
        case req := <-hp.inbound:
            hp.mu.Lock()
            last, exists := hp.dedup[req.HostId]
            if exists && time.Since(last) < 2*time.Second {
                hp.mu.Unlock()
                continue // 合并 2s 内重复心跳
            }
            hp.dedup[req.HostId] = time.Now()
            hp.mu.Unlock()
            batch = append(batch, req)

        case <-ticker.C:
            if len(batch) == 0 {
                continue
            }
            for _, req := range batch {
                processHeartbeat(req)
            }
            batch = batch[:0]

            // 清理过期的 dedup 记录
            hp.mu.Lock()
            now := time.Now()
            for id, t := range hp.dedup {
                if now.Sub(t) > 10*time.Second {
                    delete(hp.dedup, id)
                }
            }
            hp.mu.Unlock()
        }
    }
}
```

## 7. 安全实现

- **mTLS 证书**：使用 Go 的 crypto/tls，内核加载 CA 证书与服务器私钥，Agent 加载客户端证书。证书生成可用内置 CA（基于 crypto/x509）。
- **指令签名**：内核使用 hmac.New 对命令体签名，Agent 验签。HMAC 密钥未配置时，Agent 启动时即发出 SECURITY ALERT 告警，运行时拒绝所有远程命令并记录安全事件。签名覆盖 `cmdID` + `action` + 所有 `params`（按 key 排序），防止参数篡改。
- **Agent 权限**：Agent 以非 root 用户运行，通过 sudo 规则仅允许执行必要的网络/服务管理命令。命令执行白名单严格限制可执行路径，禁止 `sh`、`cmd` 等通用 shell，并实施元字符注入检测。
- **命令参数验证**：`RunCmdTimeout` 在执行前检查所有参数是否包含 shell 元字符（`|;&\`$()<>{}\n\r`），发现危险字符立即拒绝执行，防止命令注入攻击。
- **环境变量注入防护**：扩展执行器在注入环境变量前验证键名不含 `=` 和换行符、值不含换行符，防止通过环境变量注入攻击宿主进程。
- **SessionID 安全**：Agent 注册时生成的 SessionID 随机后缀从 4 字节（32 位熵）增至 16 字节（128 位熵），防止会话 ID 被猜测。`rand.Read` 错误不再被忽略，失败时记录日志并降级为确定性填充。
- **命令请求验证**：`ExecuteCommand` 接口新增 `CommandId` 和 `HostId` 空值校验，防止伪造命令确认。
- **内核加固**：内核自身运行 ASSCOR 自评估，得分低于 90 发出告警；监听端口仅对 Agent 网段开放。
- **文件权限**：审计日志与评估结果文件权限收紧为 0600，仅限运行用户读写，防止敏感数据泄露。
- **扩展执行安全**：外部工具适配器执行前解析符号链接至最终路径，防止通过符号链接绕过白名单限制。
- **日志完整性**：日志字段在写入前经过 `sanitizeLogField` 过滤换行符，防止日志注入攻击；写入后调用 `Sync()` 确保数据落盘。

## 11. 微内核架构（μKernel）详细设计

### 11.1 架构分层

ASSCOR μKernel 采用插件化微内核架构，分为四层：

```
┌─────────────────────────────────────────────────────┐
│  通信层  (gRPC/JSON RPC + mTLS)                      │
│  KernelService: Register, Heartbeat                  │
│  AgentService:  GetSnapshot, ExecuteCommand, StreamLogs│
├─────────────────────────────────────────────────────┤
│  服务层  (Service Implementations)                   │
│  KernelServiceImpl / AgentServiceImpl                │
│  协议编解码 (JSON Codec) + 请求路由分发               │
├─────────────────────────────────────────────────────┤
│  内核层  (Plugin Kernel Core)                        │
│  ┌──────────┬──────────┬──────────┬───────────┐     │
│  │ 插件注册  │ 生命周期   │ DI 容器  │ 扩展点     │     │
│  │ Registry │ Lifecycle │ Container│ Extensions│     │
│  ├──────────┴──────────┴──────────┴───────────┤     │
│  │         消息总线 (Event Bus — pub/sub)       │     │
│  └────────────────────────────────────────────┘     │
├─────────────────────────────────────────────────────┤
│  模块层  (Plugin Modules — 7 个内置插件)              │
│  Heartbeat│SPC│CTI│Assessor│Policy│Commander│Collector│
└─────────────────────────────────────────────────────┘
```

### 11.2 核心组件

#### 11.2.1 Plugin 接口 — 插件契约

所有内核模块必须实现 `Plugin` 接口，声明其元信息、依赖关系及生命周期回调：

```go
type Plugin interface {
    Info()         PluginInfo           // 名称、版本、描述、作者
    Dependencies() []PluginDependency   // 声明所需的外部接口
    Init(ctx, kernel) error             // 初始化：注册到 DI 容器、声明扩展点
    Start(ctx) error                    // 启动：订阅消息总线、启动后台任务
    Stop(ctx) error                     // 停止：优雅退出、释放资源
    State()        PluginState          // 当前状态
}
```

**插件状态机：**

```
Unregistered → Registered → Initialized → Started → Running
                                                  ↓
                                            Stopping → Stopped
                                                  ↓
                                               Failed
```

**增强接口：**
- `PriorityPlugin`：声明启动/停止优先级（数值越小越先启动，越后停止）
- `HealthCheckable`：提供运行时健康检查
- `ConfigurablePlugin`：支持运行时配置热更新

#### 11.2.2 DI 容器 — 依赖注入

轻量级依赖注入容器，通过类型映射实现接口与实现的解耦：

```go
type Container struct {
    bindings map[reflect.Type]interface{}  // 接口类型 → 实现实例
    aliases  map[string]reflect.Type       // 命名别名 → 接口类型
}

// 核心方法
func (c *Container) Bind(iface, impl interface{})
func (c *Container) Resolve(iface interface{}) (interface{}, bool)
func (c *Container) Inject(target interface{}) error  // struct tag: `inject:"name"`
```

**注入方式：**
1. **类型注入**：`c.Bind((*AssessorInterface)(nil), assessorModule)`
2. **命名注入**：`c.BindNamed("config", (*Config)(nil), cfg)`
3. **Struct Tag 注入**：`type Foo struct { Assessor AssessorInterface \`inject:"assessor"\` }`

#### 11.2.3 消息总线 — 模块间通信协议

基于发布/订阅模式的内部事件总线，实现模块间的松耦合通信：

```go
type Bus struct {
    subscribers map[string][]subscriber  // topic → 订阅者列表
}

// 核心操作
func (b *Bus) Subscribe(topic, id string, handler MessageHandler)
func (b *Bus) Publish(ctx context.Context, msg Message)
func (b *Bus) PublishSync(ctx context.Context, msg Message) []error
```

**发布模式：**

| 模式 | 方法 | 语义 | 适用场景 |
|------|------|------|----------|
| 异步发布 | `Publish` | 非阻塞，每个订阅者在独立 goroutine 中执行 | 低优先级通知（如 `agent.heartbeat`、`config.reloaded`） |
| 同步发布 | `PublishSync` | 阻塞，依次调用所有订阅者，返回错误列表 | 关键业务消息（如 `assessor.result`、`policy.action`、`spc.updated`） |

**v1.5 修复**：原 `assessor.result`、`policy.action` 等关键消息使用异步 `Publish`，可能导致消息丢失或处理顺序不一致。现改为 `PublishSync` 同步发布，确保订阅者处理完毕后才继续，并记录发布错误。

**预定义消息主题：**

| 主题 | 发布者 | 订阅者 | 发布模式 | 说明 |
|------|--------|--------|----------|------|
| `agent.registered` | Heartbeat | Policy, Assessor | 异步 | Agent 注册事件 |
| `agent.heartbeat` | Heartbeat | Assessor | 异步 | Agent 心跳（触发评估） |
| `agent.timeout` | Heartbeat | Policy, Commander | 异步 | Agent 超时告警 |
| `assessor.result` | Assessor | Policy | **同步** | 评估完成 |
| `policy.action` | Policy | Commander | **同步** | 自动响应动作 |
| `spc.updated` | SPC | Assessor, Policy | **同步** | SPC 态势修正更新 |
| `cti.threat_detected` | CTI | Assessor, Policy | 异步 | 威胁情报更新 |
| `adapter.findings` | AdapterIntegration | Assessor | 异步 | 适配器发现注入评估 |

**扩展点（生命周期钩子）：**

| 扩展点 | 触发时机 | 参数 |
|--------|----------|------|
| `kernel.pre_init` | 所有插件 Init 前 | nil |
| `kernel.post_init` | 所有插件 Init 后 | nil |
| `kernel.pre_start` | 所有插件 Start 前 | nil |
| `kernel.post_start` | 所有插件 Start 后 | nil |
| `kernel.pre_stop` | 开始关闭序列前 | nil |
| `kernel.post_stop` | 所有插件 Stop 后 | nil |
| `assessor.pre_evaluate` | 评估开始前 | hostID |
| `assessor.post_evaluate` | 评估完成后 | AssessmentResult |
| `spc.pre_calculate` | SPC 计算前 | hostID |
| `spc.post_calculate` | SPC 计算后 | SPCCorrection |

#### 11.2.4 插件生命周期管理

内核 `Bootstrap()` 按优先级顺序执行：

1. 按 `PriorityPlugin.Priority()` 排序（数值小先启动）
2. 遍历插件执行 `ConfigurablePlugin.Configure()`（若实现）
3. 解析 `Dependencies()`，从 DI 容器注入依赖
4. 执行扩展点 `kernel.pre_init`
5. 遍历插件执行 `Plugin.Init()`
6. 执行扩展点 `kernel.post_init`
7. 执行扩展点 `kernel.pre_start`
8. 遍历插件执行 `Plugin.Start()`
9. 执行扩展点 `kernel.post_start`

关闭流程 `Shutdown()` 按优先级降序逆序停止。

### 11.4 双协议栈：JSONRPC 兼容层 + gRPC 原生协议

ASSCOR μKernel 实现双协议栈通信，支持零外部依赖的 JSONRPC 兼容层和基于 `google.golang.org/grpc` 的原生 gRPC 协议：

#### 11.4.1 JSONRPC 兼容层（零外部依赖）

```
api/v1/ASSCOR.pb.go
├── 消息类型定义（RegisterRequest, HeartbeatRequest, ...）
│   └── 与 api/v1/ASSCOR.proto 规范一一对应
├── ServiceRegistry（服务注册与分发）
│   ├── Register(desc) — 注册服务方法
│   └── Dispatch(ctx, service, method, payload) — 路由到 Handler
├── ServerCodec 接口（协议编解码）
│   └── JSONCodec 实现 — 基于 JSON 的请求/响应序列化
└── MethodHandler — func(ctx, payload) -> (payload, error)
```

**兼容性保证：**
- 所有消息字段与 `.proto` 定义完全一致
- 序列化格式为 JSON（当前），未来可迁移至 Protobuf 二进制格式
- 服务名、方法名与 gRPC 规范匹配：`"ASSCOR.v1.KernelService/Register"`

#### 11.4.2 gRPC 原生协议（高性能场景）

基于 `google.golang.org/grpc` 实现的原生 gRPC 协议层，支持 Protobuf 二进制序列化和 HTTP/2 多路复用：

```
api/v1/grpc.go
├── Protobuf 消息定义（PBSnapshotRequest, PBCommandRequest, PBLogEntry, ...）
├── gRPC 服务接口
│   ├── KernelServiceServer (GetSnapshot, Register, Heartbeat)
│   └── AgentServiceServer (ExecuteCommand, StreamLogs)
├── PB ↔ JSON 转换方法
│   └── 复用现有 KernelServiceImpl / AgentServiceImpl 逻辑
└── 流式日志 (AgentService.StreamLogs, 客户端流式)

internal/kernel/grpc_server.go
├── GRPCServer 配置 (TLS/mTLS, Keepalive, MaxRecvSize)
├── 协议转换 Handler
│   ├── grpcKernelHandler → KernelServiceImpl
│   └── grpcAgentHandler → AgentServiceImpl
└── 优雅关闭 (GracefulStop)
```

**配置项（config.ini [adapter] 段）：**

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `grpc.enabled` | off | 启用 gRPC 原生协议 |
| `grpc.listen_addr` | :50052 | gRPC 监听地址 |
| `grpc.tls_enabled` | off | 启用 TLS/mTLS |
| `grpc.max_recv_size` | 4194304 | 最大接收消息大小 (4MB) |
| `grpc.keepalive_min` | 30s | 最小 Keepalive 间隔 |

### 11.5 权重热加载机制

ConfigWatcherModule 监控 `config.ini` 文件变化，自动触发权重重载：

- **轮询检测**：每 30 秒检查文件修改时间，变化时重新解析配置
- **信号触发**：监听 SIGHUP 信号，立即触发重载
- **重载范围**：域权重（AttackSurface/BusinessContinuity/OperationTrust/Resilience）、阈值、威胁系数
- **事件发布**：重载成功后发布 `config.reloaded` 事件到消息总线
- **原子性**：先解析完整配置，再更新 Assessor，避免中间状态

### 11.6 SPC 缓存持久化

SPC 模块的 CVE 缓存支持磁盘持久化，避免重启后冷启动拉取：

- **启动加载**：`Start()` 时从 `{DataDir}/spc_cache.json` 加载缓存
- **退出保存**：`fetchLoop()` 退出时（内核关闭）保存缓存到磁盘
- **原子写入**：先写临时文件，再 `os.Rename` 替换，防止写入中断导致数据损坏
- **缓存格式**：JSON 序列化，包含 CVE 列表、索引、最后更新时间

### 11.7 适配器集成模块

AdapterIntegrationModule 周期性执行 21 个外部适配器（11 个探测器 + 10 个管理类），通过 Fetch→Parse→Map→Validate 四阶段流水线将发现注入评估流程：

- **周期执行**：默认每 6 小时运行一次适配器管线（`syncLoop()`）
- **立即执行**：启动时立即执行首次同步（避免 Ticker 首次延迟）
- **并发控制**：信号量限制最大 10 个 worker，120 秒全局超时
- **结果转换**：`NormalizedFinding.ToCheckResult()` 将适配器发现映射为 CheckResult
- **事件发布**：适配器发现通过 `adapter.findings` 事件发布到消息总线
- **评分注入**：Assessor 在 `AssessFromResults()` / `Assess()` 中执行 `runAdapterPipeline()`，合并结果到评估
- **委派去重**：通过 `buildDelegatedSet()` 跳过已被外部适配器覆盖的内置检查项（13 条委派规则）
- **插件注册**：AdapterIntegrationModule 作为 Kernel Plugin 注册（v1.4 修复），确保后台同步、事件发布、按需拉取功能生效

**21 个适配器清单：**

| 类别 | P0 | P1 | P2 |
|------|:--:|:--:|:--:|
| 探测器 | Trivy, Nuclei | Lynis, OpenSCAP, Wazuh Agent, Suricata, Falco, ClamAV | OSV-Scanner, AIDE, Nikto |
| 管理类 | Ansible, NetBox | FreeIPA, Keycloak, Wazuh SIEM, Rundeck | Jira, Terraform, OpenTofu, Snipe-IT |

### 11.9 ConfigWatcher 安全类型断言

v1.5 修复：原 `ConfigWatcherModule` 在获取 Assessor 插件引用时使用裸类型断言 `p.(*AssessorModule)`，当插件类型不匹配时会直接 panic 导致内核崩溃。现改为安全类型断言 `am, ok2 := p.(*AssessorModule)`，类型不匹配时记录警告日志而非 panic，确保配置热加载过程的稳定性。

### 11.11 mTLS 证书管理

基于 Go `crypto/x509` 的内置 CA 体系：

```
启动时自动检查 certs/ 目录：
  1. 无 CA 证书 → 生成自签名 CA (RSA 4096, 10年)
  2. 无服务端证书 → 用 CA 签发 Server Cert (RSA 2048, 1年)
  3. Agent 注册时 → CSR 提交 → CA 签发 Agent Cert

mTLS 约束：
  - 最低 TLS 1.2
  - 密码套件：TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384 (优先)
  - 客户端证书必须由内核 CA 签发
  - 服务端证书必须由内核 CA 签发
```

### 11.13 安全性分析：零外部依赖架构的安全论证

ASSCOR（SSAM 1.3 的实现项目）的安全性不仅没有因为"零外部依赖 + 自研 gRPC 层"而受到实质性削弱，反而在几个关键领域得到了加强，但这也将安全责任完全转移到了团队自身的工程能力上。下面从攻击面和防御机制两个维度进行系统性辩证分析。

#### 11.11.1 安全性得到增强的领域

**消除软件供应链攻击面（最大收益）**

传统引入 `google.golang.org/grpc` 及其传递依赖链，意味着需要信任数十个第三方包（包括 `protobuf`、`x/net`、`x/sys` 等）的每个版本及其维护者。历史上这类库曾出现严重安全漏洞，如 CVE-2023-44487 HTTP/2 快速重置攻击。ASSCOR 完全自研通信层，将可审计的代码量缩减到仅由开发团队编写的 Go 标准库调用，彻底切断了这条潜在的攻击路径。对于一款安全产品而言，自身不引入不受控的外部代码，本身就是最高优先级的安全要求，显著降低了供应链攻击风险。

**强制极简攻击面**

自研的"gRPC 兼容层"本质上是一个轻量级 HTTP JSON 分发器。它没有实现完整的 HTTP/2 帧处理、HPACK 头部压缩、流多路复用等复杂逻辑，而这些恰是历史上 gRPC 漏洞的高发区域。根据安全工程基本原则，协议栈的复杂度与潜在可利用缺陷数量呈正相关，简化设计直接减少了攻击面。

**内置 CA 的无缝安全闭环**

§11.6 设计的自动签发 mTLS 机制，避免了手动管理 OpenSSL 命令和证书文件可能带来的密钥泄露、证书过期遗忘、权限配置错误等运维风险。所有证书的生成、签发、验证逻辑均由内核二进制自身完成，形成闭环且可完整审计的证书生命周期管理体系，提升了密钥管理的安全性。

#### 11.11.2 已正视并通过设计缓解的潜在风险

**自研代码可能引入逻辑漏洞**

新开发的 EventBus、DI 容器、JSON Codec 等组件属于"新造的轮子"，未经过开源社区长时间实战打磨和安全审查，可能存在竞态条件、内存泄漏、序列化注入等潜在缺陷。

| 风险类别 | 缓解措施 | 对应白皮书 |
|----------|----------|-----------|
| 并发资源耗尽 | Goroutine 池 + 信号量限制，防止无限制 goroutine 爆炸 | §6 并发与性能设计 |
| 组件初始化状态混乱 | 严格排序的依赖注入 Bootstrap 流程 | §11.2.4 插件生命周期管理 |
| Panic 扩散 | EventBus 发布时对每个订阅者的 panic 进行 recover 隔离，并通过 BusMetrics 跟踪 panic/error/message 计数 | [bus.go](file:///f:/ASSCOR/internal/kernel/bus.go) |

**缺失 gRPC 生态的安全拦截器**

标准 gRPC 框架提供认证、日志审计、流量限流、熔断降级等安全拦截器组件开箱即用。自研通信层需要团队自行实现这些安全控制功能。

| 缺失能力 | 补偿措施 | 对应白皮书 |
|----------|----------|-----------|
| 传输认证 | Go 标准库 mTLS (TLS 1.2+)，安全性等同于标准 gRPC 传输层保障 | §11.6, §7 |
| 命令防篡改 | 内核下发的每条命令均携带 HMAC-SHA256 签名，Agent 验证通过后方可执行 | §4.1, §7 |
| 审计日志 | LogCollector 模块追加写入，日志不可删除，文件权限 0600 | §3.1.6, [collector.go](file:///f:/ASSCOR/internal/kernel/collector.go) |
| Agent 权限沙箱 | 非 root 用户运行，仅 sudo 白名单执行经审计的系统管理命令 | §7 |
| 流量限流 | RateLimiter 令牌桶拦截器，自动清理过期客户端桶（5 分钟周期，30 分钟过期） | [ratelimit.go](file:///f:/ASSCOR/internal/kernel/ratelimit.go) |
| 熔断降级 | CircuitBreaker 熔断拦截器，窗口条目上限 1000 防止内存无限增长 | [circuitbreaker.go](file:///f:/ASSCOR/internal/kernel/circuitbreaker.go) |
| 审计拦截器 | AuditLogInterceptor 记录每次请求的客户端、服务、方法、耗时与结果 | [interceptor.go](file:///f:/ASSCOR/internal/kernel/interceptor.go) |

**JSON 解析可能遭遇注入式攻击**

JSON 作为文本协议存在一定的解析安全风险。

- **缓解措施**：所有消息格式严格对应 `.proto` 文件定义的强类型结构，使用 Go 语言的 `json.Unmarshal` 函数将 JSON 数据解析到固定 struct 类型，该过程不执行任何动态脚本，从根本上消除了传统 JSON 注入攻击风险。此外，架构设计支持未来平滑迁移至 Protobuf 二进制格式，可进一步降低解析器攻击面。

#### 11.11.3 结论：安全天平向"可控性"倾斜

选择"零外部依赖 + 自研 gRPC 层"技术路线，本质上是**用团队自身的编码质量和安全工程能力去对抗社区库中未知的供应链风险**。对于 ASSCOR 这样一个安全评估平台自身就是关键攻击面的产品，这种决策具有合理性：

- 若团队具备扎实的系统编程能力、并发安全经验及密码学最佳实践知识，那么系统**整体安全性会显著提升**，因为攻击面已知且最小化，所有安全机制均在团队完全掌控之下。
- 若团队缺乏相关领域经验，自研组件可能成为新的安全薄弱环节，引入未被发现的逻辑漏洞。

白皮书中的设计 —— mTLS 传输加密、命令 HMAC 签名、最小权限原则、并发安全限制 —— 已经为最关键的风险点提供了明确的防御措施。因此，**只要开发团队严格按照白皮书规范实现，并辅以全面的安全审计（包括静态代码分析、动态渗透测试、模糊测试）和持续集成验证，ASSCOR（SSAM 1.3 的实现项目）的安全性不会因"零外部依赖"而降低，反而会因为自主可控性的提升而增强。**

### 13.6 与 SSAM 评估体系的集成路径

```
┌──────────────────────────────────────────────────────────────┐
│                    ASSCOR μKernel                              │
│                                                              │
│  ┌─────────────┐    assessor.result    ┌──────────────────┐  │
│  │   Assessor   │─────────────────────▶│  Policy Manager  │  │
│  │  (SSAM 1.3)  │                      │  (自动响应)       │  │

│         │                                       │            │

│  │   ATTACK     │───────────────────────────────┘            │
│  │  Module v2.0 │                                             │
│  │              │◀──── spc.updated ──── SPC Module            │
│  │  ┌────────┐  │◀──── cti.threat ──── CTI Module            │
│  │  │ 检测   │  │                                             │
│  │  │ 情报   │  │                                             │
│  │  │ 仿真   │  │                                             │
│  │  │ 评估   │  │                                             │
│  │  │ APT    │  │                                             │
│  │  └────────┘  │                                             │
│  └─────────────┘                                              │
└──────────────────────────────────────────────────────────────┘
```

**集成路径说明：**

1. **评估→检测**：Assessor 的检查结果（`checkResults map[string]bool`）输入 ATT&CK 覆盖率计算和差距分析
2. **检测→策略**：APT 攻击链检测、行为告警、信标检测通过事件总线触发策略管理器自动响应
3. **SPC→归因**：SPC 的 CVE 匹配结果可与 APT 归因的威胁行为体已知利用偏好交叉验证
4. **CTI→情报**：CTI 模块的威胁系数 μ 与 ATT&CK 威胁情报子模块共享数据源

### 13.7 并发安全

模块所有共享状态通过 `sync.RWMutex` 保护，写操作使用 `Lock()`，读操作使用 `RLock()`。所有公开方法在入口处获取锁，在 `defer` 中释放。

关键并发场景：

| 场景 | 并发风险 | 保护措施 |
|------|----------|----------|
| 规则评估写入告警 + 查询告警 | 读写竞争 | `Lock`/`RLock` |
| 攻击链重构写入 + 归因读取 | 读写竞争 | `Lock`/`RLock` |
| 信标检测写入 + 查询信标 | 读写竞争 | `Lock`/`RLock` |
| 假设自动生成 + 手动创建 | 写写竞争 | `Lock` |
